# File: .forge/report.json

# `.forge/report.json`

> This file is **data**, not code. It is a machine-written run artifact, so "components" below are the JSON schema/contract rather than classes and functions. The producer and consumers live in the modules listed under `imported_by`.

## Purpose

`.forge/report.json` is the **run report for a single execution of the `diary-update` pipeline**. It records *what ran, when, how long each step took, and how many entries/beliefs were produced*, plus a rolled-up `summary`. It sits next to `.forge/proposed-entries.json` in the transient `.forge/` artifact directory.

The report owns the "run ledger" responsibility: downstream tooling — `reasons_lib/report_gated.py`, `reasons_lib/report_belief.py`, and `reasons/api.py` — can read it to decide whether a run succeeded, how many beliefs were accepted, and what the corpus size is, **without re-executing the pipeline**.

This specific instance describes a run with:

- **17** diary entries read
- **260** beliefs proposed
- **0** accepted
- **201** total beliefs in the corpus *after* the run (i.e., unchanged by this run — it was a no-op on corpus size)

The heavy proposal volume (260) with zero acceptance is the single most interesting fact encoded here — the gate rejected/deduplicated everything.

## Key Components (schema contract)

There are no classes/functions here; the contract is the field set below.

**Top level**

| Field | Value here | Contract |
|---|---|---|
| `pipeline` | `"diary-update"` | Stable workflow identifier that produced the report |
| `started_at` | `"2026-11-22T18:00:02+00:00"` | ISO 8601, UTC offset (`+00:00`) |
| `updated_at` | same | Last write; equals terminal timestamp when finished |
| `status` | `"completed"` | Overall run status (terminal value observed) |
| `steps[]` | 2 entries | **Ordered** per-step reports |
| `completed_at` | same | Present only on terminal runs |
| `summary` | object | Roll-up of `steps[].counts` |

**Step object** (both steps share one shape)

- `name` — `"propose-beliefs"` / `"accept-beliefs"` — identifies the stage
- `status` — `"completed"`
- `started_at`, `completed_at` — ISO 8601 UTC
- `detail` — human-readable (`"proposed 260 from 17 entries"`)
- `counts` — machine-readable metrics; shape differs per step
- `duration_seconds` — float (0.01 here)

**Per-step `counts`**

- `propose-beliefs` → `{ "entries": 17, "proposed": 260 }`
- `accept-beliefs` → `{ "accepted": 0, "total_beliefs": 201 }`

**`summary`** → `{ "entries": 17, "proposed": 260, "accepted": 0, "total_beliefs": 201 }`

Note the deliberate **dual encoding**: `detail` is for humans, `counts`/`summary` for machines. Consumers should key off `counts`, never parse `detail`.

All four `summary` keys also appear in a step's `counts` — that one-to-one mapping is the core invariant (see below).

## Patterns

- **Saga / workflow-run report**: ordered `steps[]` with status + timestamps + a terminal `completed_at`, mirroring workflow-engine run records (GitHub Actions run logs, DAG runs, etc.).
- **Rollup aggregation**: `summary` is a pure reduction of `steps[].counts` by key — `entries` and `proposed` come only from `propose-beliefs`; `accepted` and `total_beliefs` come only from `accept-beliefs`.
- **Dual-encoded output**: `detail` (human) alongside `counts` (machine) in every step.
- **UTC-normalized, lexicographically sortable timestamps**: every timestamp uses `+00:00`, so string comparison equals chronological comparison.
- **Overwrite-style artifact directory**: `.forge/report.json` is rewritten per run (no run history here); the sibling `costs/2026-11-19T180331-update.json` follows the same "timestamped JSON artifact" convention.
- **Mirrored module trees**: consumers exist as both `reasons_lib/*` and `reasons/*`; contract changes must land in both.

## Flow

1. `report_belief.py` begins the `diary-update` pipeline, records `started_at`, and initializes the skeleton (`pipeline`, `status`, empty `steps`).
2. Step `propose-beliefs` reads the 17 diary entries, emits 260 proposals, and appends a step object with `counts.entries` and `counts.proposed`.
3. Step `accept-beliefs` evaluates the proposals, accepts 0, and appends `counts.accepted` plus the post-run `counts.total_beliefs` (201).
4. On success the writer sets `status: "completed"`, writes terminal `updated_at`/`completed_at`, and reduces step counts into `summary`.
5. `report_gated.py` / `api.py` later read the file, validate `status`, and act on `summary.accepted` / `summary.total_beliefs`.

In this instance `started_at == updated_at == completed_at` and each step took `0.01s`, so the whole pipeline finished within the same second — consistent with a fast/instant run or a deterministic test fixture. Do not read these timestamps as a meaningful duration.

**Transformation:** `steps[i].counts` → merged into `summary` by key. `summary` reflects **step-reported counts**, not a fresh DB query.

## Invariants

- `started_at <= completed_at`, and per step `started_at <= completed_at`.
- All timestamps are ISO 8601 with a `+00:00` UTC offset.
- Step order is fixed: `propose-beliefs` precedes `accept-beliefs`.
- `summary` mirrors step counts exactly:
  - `summary.entries == steps[propose].counts.entries`
  - `summary.proposed == steps[propose].counts.proposed`
  - `summary.accepted == steps[accept].counts.accepted`
  - `summary.total_beliefs == steps[accept].counts.total_beliefs`
- `duration_seconds ≈ (completed_at − started_at).total_seconds()` (≈ 0.01 here).
- `status == "completed"` ⇒ `completed_at` is present and every step is terminal.
- `accepted` counts **new** beliefs, so `total_beliefs` is a post-run corpus size. With `accepted == 0`, corpus size is unchanged by the run.
- `proposed` (260) is independent of `total_beliefs` (201): proposals do not imply acceptance.

## Error Handling

- This file has no control flow, so failures are encoded as **state**, not exceptions. A failing run should carry `status: "failed"` (and likely a per-step `status`/`detail`), not a traceback.
- **Consumers must validate.** `report_gated.py` and `api.py` should treat a missing, truncated, or schema-invalid file as an error themselves — the artifact gives them no protection.
- A gate should require `status == "completed"` explicitly rather than inferring success from counters — a `"running"` report may already contain partial `counts`.
- **Partial-write hazard**: a CI consumer may read mid-write. `report_belief.py` should write atomically (temp file + `os.replace`) so readers never see a JSON document with `status` but no `completed_at`.
