# `.forge/report.json`

## Purpose

`.forge/report.json` is a persisted **pipeline run report** for the `diary-update` workflow. It is not executable code and owns no algorithms; it is a machine-readable artifact that records:

- which pipeline ran,
- when it started/updated/completed,
- the status of each pipeline step,
- per-step counters and durations,
- a denormalized summary of the run.

Its role is to be written by the diary-update pipeline and read by reporting/API/gating code such as `reasons/api.py`, `reasons_lib/report_belief.py`, and `reasons_lib/report_gated.py`. Tests in `tests/test_report_belief.py` and `tests/test_report_gated.py` likely pin the expected schema/behavior.

This specific file records a successful but no-op-ish update:

- `17` diary entries were processed,
- `260` beliefs were proposed,
- `0` were accepted,
- the belief store still contains `201` beliefs.

The identical timestamps and `0.01` second durations suggest either a very fast run or a synthetic/test-fixture run, but the schema is production-shaped.

## Key Components

Since this is JSON, the “components” are fields and their contracts.

### Top-level run metadata

- `pipeline`: `"diary-update"` — identifies the producer/workflow.
- `started_at`, `updated_at`, `completed_at`: ISO-8601 UTC timestamps with `+00:00`.
  - In this file all are `2026-11-24T18:00:07+00:00`.
  - `updated_at` is the last mutation time; `completed_at` is terminal completion time.
- `status`: `"completed"` — the overall run reached terminal success.
- `steps`: ordered array of step reports.
- `summary`: aggregate counters for quick consumption.

### `steps[]`

Each step entry has:

- `name`: step identifier.
- `status`: step-level status; here `"completed"`.
- `started_at`, `completed_at`: step timing.
- `detail`: human-readable prose summary.
- `counts`: machine-readable counters specific to the step.
- `duration_seconds`: numeric duration, here `0.01`.

#### `steps[0]`: `propose-beliefs`

```json
"counts": {
  "entries": 17,
  "proposed": 260
}
```

Contract: this step read `17` source entries and produced `260` proposed belief records. The matching `detail` string is:

> `"proposed 260 from 17 entries"`

The numeric source of truth should be `counts`, not `detail`.

#### `steps[1]`: `accept-beliefs`

```json
"counts": {
  "accepted": 0,
  "total_beliefs": 201
}
```

Contract: this step attempted acceptance and accepted `0` beliefs. The total belief count after the step is `201`. The `detail` string is:

> `"accepted 0 beliefs"`

Again, consume `counts.accepted` and `counts.total_beliefs`, not the prose.

### `summary`

```json
{
  "entries": 17,
  "proposed": 260,
  "accepted": 0,
  "total_beliefs": 201
}
```

This is a denormalized aggregate of the per-step counters. It exists so readers do not have to traverse `steps[]` just to display the headline numbers.

## Patterns

### 1. Pipeline run manifest / execution report

The file follows a common “run report” pattern:

- top-level pipeline identity,
- lifecycle timestamps,
- terminal status,
- ordered step records,
- summary counters.

This makes it suitable for CLI rendering, API responses, dashboards, and test assertions.

### 2. Ordered step log

`steps` is ordered by execution. Here the order is meaningful:

1. `propose-beliefs`
2. `accept-beliefs`

The acceptance step logically depends on candidate beliefs produced by the proposal step.

### 3. Denormalized summary

`summary` duplicates data already present in `steps[]`. This is intentional for read convenience. The invariant is that `summary` must stay consistent with the step counters.

### 4. Human-readable `detail` plus machine-readable `counts`

Each step carries both:

- `detail`: prose for humans,
- `counts`: stable numeric data for programs.

This is a good separation: consumers should not parse English strings.

### 5. Snapshot artifact consumed by multiple layers

The file is read by API/reporting/gating modules and tests. That means schema changes ripple into:

- `reasons/api.py`
- `reasons_lib/report_belief.py`
- `reasons_lib/report_gated.py`
- `tests/test_report_belief.py`
- `tests/test_report_gated.py`

The duplicated `reasons/` and `reasons_lib/` trees suggest two packaging/entry-point surfaces may share the same artifact contract.

## Flow

The implied execution flow is:

1. The `diary-update` pipeline starts and records `started_at`.
2. It runs `propose-beliefs`.
   - Reads `17` entries.
   - Produces `260` proposed beliefs.
   - Writes step status `completed`, counts, and duration.
3. It runs `accept-beliefs`.
   - Evaluates proposals.
   - Accepts `0` beliefs.
   - Records total belief count `201`.
   - Writes step status `completed`, counts, and duration.
4. The pipeline writes/updates the `summary`.
5. The pipeline marks the overall report `status: "completed"` and sets `completed_at`.
6. Consumers read `.forge/report.json` to:
   - expose run status,
   - render a report,
   - validate pipeline completion,
   - or gate downstream behavior.

In this instance, no acceptance occurred, but the pipeline still completed successfully. That is an important distinction: **pipeline completion is not the same as belief acceptance**.

## Invariants

The file implies these rules:

1. `status` and step statuses are terminal values here: `"completed"`.
2. `completed_at` is present when the run is completed.
3. Timestamps are ISO-8601 UTC strings ending in `+00:00`.
4. `steps` is ordered; `propose-beliefs` precedes `accept-beliefs`.
5. `summary.entries` equals `steps[0].counts.entries`.
6. `summary.proposed` equals `steps[0].counts.proposed`.
7. `summary.accepted` equals `steps[1].counts.accepted`.
8. `summary.total_beliefs` equals `steps[1].counts.total_beliefs`.
9. Counts are non-negative integers.
10. `duration_seconds` is a non-negative number.
11. `detail` is human-readable and should not be treated as stable machine data.
12. `accepted: 0` does not invalidate a `completed` status in this sample.

## Error Handling

There is no explicit error field in this schema. Error handling is not performed by the JSON file itself; it is the responsibility of the writer and reader modules.

Implications for maintainers:

- A failed pipeline would likely be represented by a non-`"completed"` top-level `status`, a non-`"completed"` step `status`, and/or missing `completed_at` fields.
- `detail` should not be used as a structured error channel.
- Readers should tolerate partial reports if they can observe the file while the pipeline is still running.
- Readers should handle malformed/missing JSON defensively, since this is a file-backed contract.
- The sample contains no `error`, `errors`, `message`, or `exception` field, so any failure payload convention must be defined elsewhere in the writer/reader code.
