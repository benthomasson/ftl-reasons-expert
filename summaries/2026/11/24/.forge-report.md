# `.forge/report.json` — Pipeline Run Report / Ledger

## Purpose

This file is **not source code** — it is a machine‑generated **execution report** (a run ledger/manifest) for a pipeline called `diary-update`. It records *when* a run happened, *which steps* ran, *how each step finished*, and *aggregate counts* for the run.

Its responsibility is **observability and auditability**, not logic:
- Persist the outcome of a `diary-update` invocation.
- Give downstream tooling (reports, gates, tests) a stable, structured record of a run.
- Provide human‑readable `detail` strings alongside machine‑parsable `counts`.

It lives in `.forge/`, alongside `.forge/proposed-entries.json`, which suggests `.forge/` is the working/state directory of a "forge" process that proposes and accepts beliefs into the `reasons` belief store.

> Note: the "Imported By" list shows files like `reasons_lib/report_belief.py`, `reasons_lib/report_gated.py`, `reasons/api.py`, and their tests. JSON has no runtime contract, so this is better read as **"referenced by"** — those modules and tests read/write/inspect this path, not Python-`import` it.

## Key Components

### Top-level envelope

| Field | Value | Contract |
|---|---|---|
| `pipeline` | `"diary-update"` | Identifies which pipeline produced the report. |
| `started_at` / `updated_at` / `completed_at` | ISO 8601 with offset (`2026-11-23T18:00:09+00:00`) | Chronological lifecycle of the run. All three are identical here — the run completed in the same second. |
| `status` | `"completed"` | Terminal state of the pipeline (presumably one of `running`/`completed`/`failed`). |
| `steps` | array of step objects | Ordered execution log. |
| `summary` | object | Denormalized roll-up of counts for cheap consumption. |

### Step object schema

Each element of `steps` shares a uniform shape:

```json
{
  "name": "propose-beliefs",
  "status": "completed",
  "started_at": "...",
  "completed_at": "...",
  "detail": "proposed 260 from 17 entries",
  "counts": { "entries": 17, "proposed": 260 },
  "duration_seconds": 0.01
}
```

- **`name`** — stable step identifier (`propose-beliefs`, `accept-beliefs`).
- **`status`** — per-step state; independent of the top-level pipeline status.
- **`detail`** — human-readable summary string.
- **`counts`** — step-specific, arbitrary key/value numeric map (different steps carry different keys).
- **`duration_seconds`** — non-negative float.

The two observed steps:
1. **`propose-beliefs`** — ingested 17 diary entries and emitted 260 proposed beliefs (`counts.entries=17`, `counts.proposed=260`).
2. **`accept-beliefs`** — attempted acceptance of proposed beliefs; `accepted=0`, and `total_beliefs=201` (the current store size after acceptance).

### `summary` object

```json
{ "entries": 17, "proposed": 260, "accepted": 0, "total_beliefs": 201 }
```

This is a flattened merge of the `counts` maps across steps — the canonical place for consumers that don't want to walk `steps`.

## Patterns

1. **Pipeline/step journal** — a small, append-style execution log: each step has its own lifecycle (`started_at` → `completed_at`, `status`), mirroring a WAL or CI-run report.
2. **Denormalization for readers** — `summary` duplicates `steps[*].counts`. The journal is the source of truth; the summary is a convenience view.
3. **Dual encoding** — every step carries both a human string (`detail`) and a machine object (`counts`).
4. **Envelope + payload** — a fixed top-level schema (`pipeline`, timestamps, `status`, `steps`, `summary`) that is pipeline-agnostic, with step-specific `counts` as the extensible payload.
5. **ISO 8601 UTC timestamps with explicit offset** — all times are timezone-aware, avoiding ambiguity in logs.

## Flow

Reading the report as the result of a run:

1. Pipeline `diary-update` starts → report is created with `pipeline`, `started_at`, `status` (probably `"running"`), empty `steps`.
2. **Step 1 — `propose-beliefs`**: reads 17 entries, produces 260 proposals, appends a step record with `counts={entries, proposed}`.
3. **Step 2 — `accept-beliefs`**: attempts to accept proposals; records `accepted=0` and the resulting store size `total_beliefs=201`.
4. Pipeline finalizes: `status="completed"`, `completed_at` set, `updated_at` refreshed, and `summary` computed from step counts.

For consumers (e.g., `report_gated.py`), the typical flow is: load JSON → check `status == "completed"` → read `summary` (`accepted`, `total_beliefs`) → make a gating/reporting decision.

## Invariants

- **Envelope schema is stable** — `pipeline`, `started_at`, `updated_at`, `status`, `steps`, `summary` are always present.
- **Timestamps are ISO 8601 with timezone offset** — never naive/local.
- **Steps are ordered** in execution order, and each step's `completed_at ≥ started_at`.
- **`duration_seconds` is non-negative** and roughly equals `completed_at − started_at`.
- **`summary` is a projection of `steps[*].counts`** — the two must agree (`entries=17`, `proposed=260`, `accepted=0`, `total_beliefs=201` all match their step counts).
- **Terminal status implies a completion timestamp** — `status="completed"` ⇒ `completed_at` is populated.
- **`accepted` does not inflate `total_beliefs`** — here `accepted=0` leaves `total_beliefs=201`, indicating the 201 figure is the store size after acceptance, not a pre-existing count plus accepted. A maintainer should confirm whether `total_beliefs` is *pre* or *post* acceptance; the numbers here only make sense if it's the resulting store size.

## Error Handling

This file itself cannot "handle" errors — it's inert JSON. The error semantics belong to its producers/consumers:

- **Producer side** (whatever writes the report): a failed step presumably records `status="failed"` on that step (and likely on the pipeline), possibly with an error string in `detail`. There is no error field in the observed schema, so failure details must be encoded in `status`/`detail` or a step-specific `counts` key.
- **Consumer side** (`report_belief.py`, `report_gated.py`): must be defensive — tolerate a missing/partial/`running` report, since a run may be interrupted before `completed_at`/`summary` is written. The gate should treat non-`completed` status as "don't proceed."
- **Silent success here**: with `accepted=0`, the pipeline still reports `status:"completed"` — acceptance producing zero beliefs is treated as a normal, non-error outcome. A gate that equates "completed" with "something changed" would be wrong.
