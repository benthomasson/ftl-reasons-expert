## Purpose

It records what happened during a single pipeline execution: when it started, which steps ran, how many diary entries were processed, how many beliefs were proposed/accepted, and the resulting belief-store total.

## Patterns

- **Run manifest / audit artifact**: The file is a serialized record of one pipeline execution, suitable for logs, dashboards, CLI output, or API responses.
- **Staged pipeline reporting**: Work is represented as an ordered `steps` array. Each step has its own status, timestamps, detail string, counts, and duration.
- **Denormalized summary**: `summary` duplicates the useful final metrics from individual steps so consumers do not have to inspect the entire `steps` array.
- **Status-driven lifecycle**: The top-level `status` and per-step `status` fields encode lifecycle state. This file only demonstrates the success path (`"completed"`), but the schema clearly supports non-terminal or failed states.
- **Human-readable + machine-readable pairing**: Each step has both structured `counts` and a `detail` string like `"proposed 260 from 17 entries"`.

## Flow

The intended control flow is:

1. The `diary-update` pipeline starts.
2. It initializes a report with `pipeline`, `started_at`, `updated_at`, and `status`.
3. It runs `propose-beliefs`, recording:
   - number of entries read,
   - number of beliefs proposed,
   - step start/completion timestamps,
   - duration.
4. It runs `accept-beliefs`, recording:
   - number of beliefs accepted,
   - resulting total belief count.
5. It finalizes the report by setting:
   - `status: "completed"`,
   - `completed_at`,
   - `updated_at`,
   - the aggregate `summary`.
6. Consumers read the report and inspect `status`, `summary`, or individual `steps` records.

In this execution, both steps completed within the same timestamp second. The per-step `duration_seconds` fields are `0.01`, but the top-level timestamps have only whole-second precision, so the elapsed wall-clock time cannot be reconstructed precisely from the timestamps alone.

## Invariants

A developer maintaining this report format should preserve these rules:

- `steps` is ordered. For the `diary-update` pipeline, `propose-beliefs` comes before `accept-beliefs`.
- `summary.entries` should match `steps[0].counts.entries`.
- `summary.proposed` should match `steps[0].counts.proposed`.
- `summary.accepted` should match `steps[1].counts.accepted`.
- `summary.total_beliefs` should match `steps[1].counts.total_beliefs`.
- When top-level `status` is `"completed"`, `completed_at` and `summary` are expected to be present.
- Timestamps use ISO-8601 with an explicit UTC offset (`+00:00`).
- `total_beliefs` is the belief-store total after acceptance. It is **not** derived as `proposed - accepted`; here 260 were proposed, 0 accepted, and the total remained 201.
- `accepted` should never exceed `proposed` for a normal proposal/acceptance run, though this file only demonstrates `0 <= 260`.
- There is no `schema_version` field, so consumers must be tolerant of schema evolution or coordinate changes carefully.

## Error Handling

The JSON file itself has no control flow or exception behavior. Error semantics are encoded in the `status` fields:

- This report represents a successful run because the top-level status and both step statuses are `"completed"`.
- There is no explicit `error`, `exception`, or `message` field in this schema snapshot.
- If a step fails, a producer would need to represent that through `status`, `detail`, or an expanded schema. Consumers should not assume every report has the same successful shape.
- A consumer that assumes `completed_at` or `summary` always exists may break on an in-progress or failed report; robust readers should check `status` first.
