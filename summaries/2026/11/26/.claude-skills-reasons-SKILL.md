# `.claude/skills/SKILL.md` — Explanation

## Purpose

This file is a **Claude Code skill definition** (not application code). Its job is to teach the Claude agent how to operate the `reasons` CLI — a belief-network manager where nodes are justified by other nodes rather than independent facts. The skill registers the slash command `/reasons <subcommand>` and constrains what the agent is allowed to do (only `reasons` invocations, plus read-only filesystem tools).

The critical distinction this file introduces is `reasons` vs `beliefs`:
- `beliefs` = flat registry of independent facts (staleness = source file changed)
- `reasons` = DAG of justified conclusions (staleness = upstream belief retracted, propagating as a cascade)

The skill file is essentially a **behavioral contract**: given natural language ("the threshold is calibration based on X"), Claude must translate that into a specific `reasons add ...` invocation with correct `--sl` antecedents, kebab-case node IDs, and a `--source` path.

## Key Components

### YAML frontmatter (lines 1–6)
```yaml
name: reasons
description: Reasons — track justified beliefs with automatic retraction cascades and restoration
argument-hint: "[init|add|retract|assert|challenge|defend|convert-to-premise|summarize|nogood|trace|status|show|explain|search|list|hash-sources|check-stale|compact|propagate|import-beliefs|import-json|export|export-markdown|log] [args...]"
allowed-tools: Bash(reasons *), Bash(cd * && uv run reasons *), Bash(uvx *reasons*), Read, Grep, Glob
```

- `argument-hint` — this is the **public contract** of subcommands; note `summarize` and `import-json` are listed but not documented in the body (a drift risk).
- `allowed-tools` — the agent may only run `reasons` (three installation flavors), read files, grep, and glob. It cannot run arbitrary bash.

### Core concept glossary (lines 18–28)
Defines the domain vocabulary used throughout:
- **Premise** — node with zero justifications, IN by default (created by `add` without `--sl`/`--cp`)
- **SL justification** — "Support List": IN iff *all* antecedents IN
- **Multiple justifications** — node is IN if *any* justification is valid (OR-semantics over justifications, AND-semantics within each)
- **Cascade** — retraction of a node transitively flips dependents OUT
- **Outlist** — non-monotonic justification: node is IN unless a specific outlist node is IN
- **Nogood** — mutually-exclusive set; triggers dependency-directed backtracking
- **Challenge/Defend** — dialectical layer built on top of outlist

### Subcommand reference (lines 32–256)
Each subcommand documents its CLI surface. Notable, non-obvious semantics:

| Subcommand | Contract worth remembering |
|---|---|
| `add` | Three forms: bare premise, `--sl a,b,c`, `--unless y`; also `--source`, `--label` |
| `retract` | Marks OUT; cascade handled by tool — **do not manually retract dependents** |
| `assert` | Marks IN; restores dependents. Insufficient after import (see `convert-to-premise`) |
| `explain` | Forward trace of *why* a node is IN/OUT (debugging) |
| `trace` | Backward trace to *which premises* support a conclusion |
| `challenge` | Creates a challenge node (IN) + appends to target's outlist → target OUT immediately |
| `defend` | Creates defense node neutralising a challenge → challenge OUT, target restored |
| `nogood` | Backtracking picks *premise with fewest dependents* (minimal disruption) |
| `convert-to-premise` | Strips justifications; fixes contextual (not logical) import dependencies |
| `compact` | Token-budgeted; priority = nogoods (never dropped) → OUT → IN by dependent count |
| `check-stale` | SHA-256 comparison of stored hash vs current file; **exit 1** if stale |
| `propagate` | Full recompute of all truth values (idempotent) |

### Common workflows (lines 258–360)
Nine worked examples. Themost important one for maintainers is `velocity-constraint` — it demonstrates the **three-level dialectical chain** (challenge → defend → challenge-the-defense) and shows that `defense-` prefix node IDs are auto-generated as `defense-<challenge-id>`.

### Post-command obligations (lines 362–370)
Prescriptive guidance: after `retract`, `challenge`, `defend`, `import-beliefs`, `nogood`, `explain`, `trace`, the agent **must summarize** the cascade/justification chain in plain language. This is the skill's output contract with the user.

### Storage note (lines 372–374)
`reasons.db` (SQLite) not markdown. The rationale given — ACID transactions for cascades touching 20+ nodes — is the primary reason this tool differs architecturally from `beliefs`.

## Patterns

1. **Progressive fallback execution** (lines 12–16). The agent is instructed to try, in order:
   - `reasons $ARGUMENTS` (installed tool)
   - `cd ~/git/ftl-reasons && uv run reasons $ARGUMENTS` (dev clone)
   - `uvx --from ftl-reasons reasons $ARGUMENTS` (ephemeral)
   
   This permissive pattern keeps the skill working across dev machines, CI, and remote installs.

2. **Natural-language → CLI compilation.** `add` explicitly instructs the agent to:
   - kebab-case the key phrase as node ID
   - extract description text
   - identify dependencies → `--sl`
   - identify source → `--source repo:path`
   
   This is a lightweight "DSL translator" pattern — the skill file *is* the translator spec.

3. **Read-only / mutate-only separation via tool allowlist.** `allowed-tools` gives `Read`, `Grep`, `Glob` (inspection) plus `Bash(reasons *)` (mutation). No `Edit`/`Write` — the agent cannot corrupt the DB or accidentally edit `beliefs.md`.

4. **Non-monotonic inference via outlist + nogood + challenge/defend.** Three layers of defeasibility:
   - `--unless` (static, declarative)
   - `nogood` (contradiction → backtracking)
   - `challenge`/`defend` (dynamic, argumentative)
   
   This mirrors TMS (Truth Maintenance Systems) / ATMS conventions.

5. **Generated-artifact discipline.** `export-markdown -o beliefs.md` produces a file that is explicitly *not* an input: "The output is generated — operate through `reasons`, not by editing the markdown."

6. **Priority-tiered truncation.** `compact --budget N` has an explicit drop order: nogoods invariant → OUT nodes → IN nodes by dependent-count descending. This makes the most load-bearing content survive token pressure.

## Flow

The control flow is *agentic*, not code-execution flow. When a user types `/reasons retract foo`:

1. **Dispatched:** Claude reads `argument-hint` and matches `retract` to the "### `retract`" section.
2. **Resolved:** Claude tries the three run commands, in order, passing `retract foo` through `$ARGUMENTS`.
3. **Executed:** `reasons retract foo` mutates `reasons.db`, prints cascade.
4. **Reported:** Claude executes the "After Any Command" block — reports what cascaded, suggests `status`.
5. **Follow-up resolution (optional):** If the user asks "why?", Claude runs `reasons explain foo`, then **summarizes the justification chain in plain language**.

For `add`, the interesting transformation is **natural-language → command**:
```
"The threshold is tool-use calibration, based on beliefs-improve-accuracy"
         │
         ▼
reasoning in Claude's head using "### add" rules
         │
         ├─ node id:  threshold-is-calibration       (kebab-case)
         ├─ text:     "The threshold is tool-use calibration, not intelligence"
         ├─ sl:       beliefs-improve-accuracy
         └─ source:   (optional, from context)
         │
         ▼
reasons add threshold-is-calibration "The threshold is tool-use calibration, not intelligence" --sl beliefs-improve-accuracy
```

For `challenge`/`defend`, note the **immediate recompute**: "Target goes OUT immediately, cascading to dependents." There is no deferred batching — each command produces an observable DB state change.

## Invariants

These are rules the file enforces on the *agent*, not runtime checks the tool performs:

1. **Do not manually retract dependents.** (line 70, bold) The cascade is the single source of correct propagation; manual dependent retraction desynchronises the graph.

2. **`reasons assert` is not a fix for contextual imports.** (line 130) After `import-beliefs`, `assert` marks the node IN but leaves the invalid SL justification — it will flip OUT on the next `propagate`. Only `convert-to-premise` removes the justification and makes the fix stable.

3. **`beliefs.md` from `export-markdown` is write-only from the agent's perspective.** It is generated output; editing it does nothing on the next recompute (line 232, 348).

4. **`--sl` means AND-of-antecedents; multiple justifications are OR-of-justifications.** (line 24) This is the core TMS semantics; inversions here would invert the entire network's truth policy.

5. **`check-stale` exit code encodes staleness.** Exit 1 = at least one stale node. Callers must not treat non-zero as a generic error (line 234).

6. **Nogoods are never dropped from `compact` output.** (line 244) Even under tight token budget, contradictions must surface because they trigger backtracking.

7. **Source paths resolve as `~/git/<repo-name>/<path>`.** (line 237) Any code that hashes or validates sources must use this expansion or `check-stale` will silently fail to detect changes.

8. **SQLite is the store, not markdown.** (line 372) Concurrent cascades require ACID; markdown-based approaches (as in `beliefs`) cannot guarantee atomic retraction sets.

## Error Handling

This is a markdown skill spec, so error handling is expressed as **agent behavior** + **CLI exit semantics**, not try/except blocks:

- **Installation failure:** handled by the 3-tier fallback (`reasons` → `uv run` → `uvx`).
- **Stale sources:** `check-stale` produces exit code 1 (line 234) — the agent should surface this as "found stale sources" rather than a crash.
- **Invalid node IDs:** not specified. Assumed to be handled by the CLI (probably an error message + non-zero exit). The agent will propagate any non-zero exit as a run failure.
- **Semantic mis-configuration (contextual dependency imported as SL):** not caught by the tool; the skill explicitly documents the fix (`convert-to-premise`, lines 124–130). This is an important **latent failure mode**: `import-beliefs` succeeds, nodes go OUT, and the reason is not obvious from `status` alone — the user must invoke `explain`.
- **Post-command guidance as error recovery:** if in doubt, the skill tells the agent to run `status`, `explain`, or `trace`. These are the "diagnostic" subcommands and represent the tool's primary error-inspection surface.

## Beliefs

- `outlist-enables-non-monotonic-reasoning` — A justification can require nodes to be OUT via outlist, allowing "believe X unless Y" default reasoning
- `multiple-justifications-provide-alternative-support` — A node with multiple justifications remains IN as long as any one justification is valid, going OUT only when all fail
- `retraction-cascade-is-automatic-and-transitive` — Retracting a node propagates OUT status to all dependents whose justifications become invalid, without manual intervention
- `convert-to-premise-is-required-after-contextual-imports` — `reasons assert` alone does not remove an invalid SL justification after `import-beliefs`; only `convert-to-premise` removes the justification so the node stays IN across recomputations
- `storage-is-sqlite-not-markdown` — Reasons uses `reasons.db` (SQLite) to guarantee ACID transactions during multi-node cascade propagation, unlike the markdown-based `beliefs` tool
- `compact-leaf-drops-nogoods-never` — `compact` never drops nogood entries from token-budgeted output; only OUT nodes and low-load-bearing IN nodes are truncated
