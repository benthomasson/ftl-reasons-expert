# `.github/workflows/tests.yml`

## 1. Purpose

This is the **single CI gate** for the `ftl-reasons` repository. It owns one responsibility: **ensuring the full `pytest` suite passes on every supported Python version before code can land on `main`**. There is no separate lint, build, or publish workflow here — this file is the test pipeline, full stop.

It triggers on two events, both targeting `main` exclusively:

- `push` to `main` (post-merge verification)
- `pull_request` targeting `main` (pre-merge gate)

This means feature branches that don't open a PR against `main` will **never** run tests in CI.

## 2. Key Components

| Component | Detail |
|---|---|
| `on.push.branches` / `on.pull_request.branches` | Both pinned to `[main]`. No other branch triggers CI. |
| `strategy.matrix.python-version` | `["3.10", "3.11", "3.12", "3.13"]` — four independent jobs, one per version. |
| `runs-on: ubuntu-latest` | Single runner image; no self-hosted or macOS runners. |
| `actions/checkout@v4` | Standard source checkout. |
| `astral-sh/setup-uv@v5` | Installs the `uv` binary (Astral's fast Python package manager) before any Python work. |
| `uv python install ${{ matrix.python-version }}` | Downloads the specific CPython build into uv's managed location. |
| `uv run --extra test pytest tests/ -v` | The actual test invocation. `--extra test` resolves the `test` dependency group from `pyproject.toml`. `-v` enables per-test output. |

There are **no** `setup-python`, `pip install`, or virtualenv steps. Everything is delegated to `uv`.

## 3. Patterns

- **Matrix fan-out**: The `strategy.matrix` block produces 4 parallel jobs (one per Python version). GitHub Actions runs them concurrently, so the wall-clock time is roughly the slowest single-version run, not the sum.
- **`uv` as the sole package manager**: The workflow never calls `pip` or creates a `venv` manually. `uv run` implicitly resolves the lockfile, creates/uses an environment, and executes the command. This keeps the step count to three (install uv, install Python, run tests) instead of the typical five or six.
- **`--extra test` for test dependencies**: The test-only dependencies (likely `pytest` and any fixtures) are declared under a `[project.optional-dependencies] test` key in `pyproject.toml`. This keeps the production install surface clean and means the CI environment is exactly what a developer gets with `uv sync --extra test`.
- **No caching steps**: There's no `actions/cache` for `uv`'s cache or `pip` wheels. This is a tradeoff — simpler workflow, slower cold runs. If CI times become a problem, adding a cache for `~/.cache/uv` would be the obvious next step.
- **No service containers**: Tests presumably use mocks or in-process fakes (e.g., `test_pg.py` likely mocks PostgreSQL via `pgtest` or `testing.postgresql`). There's no `services:` block spinning up a database or Redis.

## 4. Dependencies

**What this workflow depends on:**

- **`pyproject.toml`** — defines the `test` extra, the project metadata, and the Python version constraints. If someone adds a new test dependency, they must add it to the `test` extra or CI will fail with an `ImportError`.
- **`tests/` directory** — all 70+ test files. The workflow invokes `pytest tests/` with no `--ignore` or `--deselect` flags, so **every** collected test must pass.
- **`tests/conftest.py`** — shared fixtures; if it imports a package that's only in the default (non-test) extras, CI would still pass, but that's a latent coupling.
- **`uv` (via `astral-sh/setup-uv@v5`)** — pinned to major version 5. A breaking change in `setup-uv` v6 could break this workflow.
- **`actions/checkout@v4`** — similarly pinned to v4.

**What depends on this workflow:**

- Nothing imports it. It's a CI configuration file, not a library. The "Imported By: `tests/test_pg.py`" entry in the repo metadata is a false positive from the analysis tool — a YAML workflow is not importable by Python code.

## 5. Flow

Execution is strictly linear within a single job; the matrix creates 4 independent linear pipelines:

```
┌─────────────────────────────────────────────────────────────┐
│  Trigger: push or PR → main                                 │
│                                                             │
│  For each python-version in [3.10, 3.11, 3.12, 3.13]:      │
│                                                             │
│  1. actions/checkout@v4                                     │
│     └─ Clone repo into $GITHUB_WORKSPACE                    │
│                                                             │
│  2. astral-sh/setup-uv@v5                                   │
│     └─ Download & install `uv` binary into $PATH            │
│                                                             │
│  3. uv python install <version>                              │
│     └─ Fetch CPython build into uv's managed Python dir     │
│     └─ (uv caches this; repeat runs are fast)               │
│                                                             │
│  4. uv run --extra test pytest tests/ -v                    │
│     └─ Resolve dependencies from pyproject.toml             │
│     └─ Create/reuse virtualenv with runtime + test deps     │
│     └─ Collect all test_*.py under tests/                   │
│     └─ Execute each test, stream -v output to GHA logs      │
│     └─ Exit 0 → step succeeds; Exit ≠ 0 → step fails       │
│                                                             │
│  ── 4 jobs all green → PR can merge / push is clean         │
│  ── Any one job red → PR is blocked / push is flagged       │
└─────────────────────────────────────────────────────────────┘
```

There is no data transformation or orchestration beyond "run pytest and report pass/fail."

## 6. Invariants

- **Branch gate**: CI only runs for `main`. A push to `dev` or a PR targeting `staging` will produce **no** workflow run. If the team ever needs multi-branch CI, the `branches` list must be expanded.
- **Python floor and ceiling**: The matrix hard-codes 3.10–3.13. If `pyproject.toml` declares `requires-python = ">=3.10"`, that's consistent. If someone bumps the floor to 3.11, the 3.10 job will either fail at `uv python install` or at dependency resolution, and the matrix will need updating.
- **All-or-nothing**: There is no `continue-on-error: true` on any step and no `if: ` conditionality. A single failing test in any Python version fails the entire workflow.
- **Test discovery is directory-based**: `pytest tests/` relies on the default `test_*.py` / `*_test.py` naming convention. A file named `tests/check_something.py` (no `test_` prefix) would be silently skipped.

## 7. Error Handling

There is essentially **no explicit error handling** in this workflow — and that's by design:

- **Step failure = job failure.** If any of the four steps exits non-zero (e.g., `uv python install 3.99` on a version that doesn't exist, or `pytest` finding 3 failures), the step is marked red, the job fails, and the remaining steps in that job are skipped. The other 3 matrix jobs are unaffected.
- **No `if: failure()` conditional steps.** There's no "upload artifacts on failure" or "notify on success" logic.
- **No `timeout-minutes`.** A hanging test (e.g., a network call in `test_llm.py` that never times out) will run until GitHub's default 360-minute timeout kills the job. This is a latent risk — a `timeout-minutes: 15` would be prudent.
- **Test-level error semantics** are handled entirely inside `pytest` and the test code itself (fixtures in `conftest.py`, `pytest.raises` blocks, etc.). The workflow is agnostic to *what* the test does; it only cares about the exit code.
- **No retry logic.** A transient network blip during `uv python install` fails the job. There's no `retry` mechanism in the workflow.

## Topics to Explore

- [file] `pyproject.toml` — Defines the `test` extra that `uv run --extra test` resolves; understanding the exact test dependencies and Python constraints is essential before modifying the CI matrix.
- [file] `tests/conftest.py` — Shared fixtures that every test file depends on; reveals whether tests are hermetic (mocked I/O) or require external services, which would explain the absence of `services:` blocks in the workflow.
- [file] `tests/test_llm.py` — Likely the most I/O-heavy test file (LLM API calls); exploring it shows how the suite avoids hitting real APIs in CI and where `timeout-minutes` would matter most.
- [general] `uv-workflow-idioms` — How `uv run --extra test` compares to the traditional `actions/setup-python` + `pip install -e .[test]` pattern; useful if you're evaluating whether to adopt `uv` elsewhere or understand the lockfile semantics.
- [repo] `.github/workflows/` — Whether there are other workflow files (lint, publish, release) or if this tests workflow is truly the only CI surface.

## Beliefs

- `ci-gates-on-main-only` — The workflow's `on.push.branches` and `on.pull_request.branches` are both `[main]`; no other branch or PR target triggers a test run.
- `test-extra-isolation-requires-pyproject` — `uv run --extra test` resolves the `test` dependency group from `pyproject.toml`; adding a test-only package without adding it to that extra will cause an `ImportError` in CI but not in a local `uv sync` (which installs all extras by default).
- `matrix-fanout-is-parallel` — The four Python-version jobs (3.10–3.13) run concurrently on separate GitHub Actions runners; a failure in the 3.12 job does not cancel the 3.11, 3.10, or 3.13 jobs.
- `workflow-has-no-timeout` — No `timeout-minutes` is set on the `test` job, so a hung test is subject only to GitHub's 360-minute default; there is no workflow-level safeguard against an infinite loop in test code.
- `pytest-discovery-is-directory-scoped` — `uv run --extra test pytest tests/ -v` restricts collection to the `tests/` directory; test files placed at the repo root or in `reasons/` or `reasons_lib/` will not be discovered by CI.
