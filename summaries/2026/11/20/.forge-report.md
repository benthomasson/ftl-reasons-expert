# File: .forge/report.json

# `.forge/report.json`

> **Note on file type:** this is a **runtime JSON artifact**, not source. The "imported by" list means `reasons/api.py`, `reasons_lib/report_belief.py`, and `reasons_lib/report_gated.py` (and their tests) load and parse this file — not Python `import` statements. Treat its schema as a contract between the pipeline writer and these readers.

## Purpose

`.forge/report.json` is the **execution report for a single run of the `diary-update` pipeline**, written under the `.forge/` working directory. It is a persisted audit/status record answering: *"What pipeline ran, when, did it succeed, and what did each stage produce?"*

Its responsibilities:

1. **Run identity & lifecycle** — `pipeline`, `started_at`, `updated_at`, `completed_at`, and a top-level `status`.
2. **Per-step bookkeeping** — an ordered list of `steps[]`, each with its own name, status, timing, human-readable `detail`, structured `counts`, and `duration_seconds`.
3. **Machine-readable summary** — a denormalized `summary` block that mirrors the important counts from the steps, so consumers (report/monitoring code) can read a flat result without walking `steps[]`.

The concrete run here is the *diary-update* for 2026-11-19: **17 diary entries → 260 proposed beliefs → 78 accepted**, against a belief base of **201 totals**.

## Key Components

### Top-level object

| Field | Type | Meaning |
|---|---|---|
| `pipeline` | string | Run kind. Here `"diary-update"` — acts as a discriminant/version tag for the run. |
| `started_at` | ISO-8601 offset datetime | When the pipeline began (`+00:00`). |
| `updated_at` | ISO-8601 | Last write to the report (equal to `completed_at` here). |
| `status` | enum-as-string | Overall run state. Here `"completed"`; expected siblings would be `running` / `failed` / `skipped`. |
| `steps` | array of step objects | Ordered list of pipeline stages, in execution order. |
| `completed_at` | ISO-8601 | When the last step finished. |
| `summary` | object | Flat aggregate results for quick consumption. |

### Step object

| Field | Meaning |
|---|---|
| `name` | Stage identifier: `"propose-beliefs"`, `"accept-beliefs"`. |
| `status` | Per-step enum-as-string, also `"completed"`. |
| `started_at` / `completed_at` | Stage timing; note these chain (see Invariants). |
| `detail` | Free-form human-readable summary (`"proposed 260 from 17 entries"`, `"accepted 78 beliefs"`). |
| `counts` | Stage-specific structured metrics — **the shape varies by stage** (see below). |
| `duration_seconds` | Float wall-clock duration for the stage. |

Stage-specific `counts`:

- `propose-beliefs`: `{ "entries": 17, "proposed": 260 }`
- `accept-beliefs`: `{ "accepted": 78, "total_beliefs": 201 }`

### `summary` object

Flat projection of the run: `entries: 17`, `proposed: 260`, `accepted: 78`, `total_beliefs: 201`. It is deliberately redundant with the step `counts` — a denormalization for cheap reads.

## Patterns

- **Schema-as-contract / DTO**: This file is a plain data transfer object. There are no functions or classes in it; the "API" is the JSON shape, and consumers such as `reasons_lib/report_belief.py` and `reasons_lib/report_gated.py` must agree with the writer on these keys.
- **Append-per-stage step log**: `steps[]` is an ordered array that grows as the pipeline progresses; each entry is self-contained (own timings, own counts). This is the classic "job step log" pattern and makes partial runs inspectable.
- **Denormalized summary**: `summary` duplicates aggregate state so readers don't need to reduce `steps[]`. This trades storage for read simplicity and introduces a sync invariant (below).
- **Enum-as-string statuses**: `status` values are plain strings (`"completed"`), not bools or codes, so new states (`"failed"`, `"running"`) can be added without schema breakage.
- **Discriminated `counts`**: `counts` is a stage-dependent bag of metrics, not a fixed struct — `propose-beliefs` reports `{entries, proposed}` while `accept-beliefs` reports `{accepted, total_beliefs}`. Readers must key off `name`/`pipeline` before interpreting `counts`.
- **Two-timestamp freshness model**: `updated_at` vs `completed_at` — during a long run these diverge; after success they converge (both `18:03:31` here). This supports a "still writing" heuristic.

## Dependencies

**Depends on (input contract):** nothing itself — it is data. It is *written* by the diary-update pipeline (proposal/acceptance stage that also produces `.forge/proposed-entries.json` and `costs/2026-11-19T180331-update.json`, whose timestamp suffix `180331` matches `completed_at`).

**Depended on by (readers):**

- `reasons/api.py` — likely surfaces the report via the programmatic API.
- `reasons_lib/report_belief.py` — renders a belief-report view of a pipeline run.
- `reasons_lib/report_gated.py` — gated variant (aggregation/reporting across runs, or gate-status reporting).
- `tests/test_report_belief.py`, `tests/test_report_gated.py` — fixture/assertion targets.

Its natural siblings are `.forge/proposed-entries.json` (the *input* to `accept-beliefs`, 260 proposals) and `costs/2026-11-19T180331-update.json` (per-run cost accounting). They share the run timestamp and should be discoverable together.

## Flow

1. **Start**: a diary-update command (likely via `reasons/cli.py` or `reasons/propose_update.py`) records `started_at = 18:00:10` and writes `status: "running"` (implied).
2. **`propose-beliefs`**: reads 17 new diary entries, proposes 260 beliefs (LLM-driven, consistent with the `reasons/llm.py` / `propose_update.py` modules). Takes **200.75 s** and finishes at `18:03:31`. Its `counts` and `detail` are appended as `steps[0]`.
3. **`accept-beliefs`**: reads the proposals, accepts **78**, leaving the belief base at **201** total (so 123 beliefs existed before this run — `201 − 78`). Takes **0.05 s** — near-instant, suggesting a batch/DB write, not another LLM pass.
4. **Finish**: `completed_at = 18:03:31`, both step statuses and top-level `status` set to `"completed"`, and `summary` is populated by projecting the two stages' counts.
5. **Consumption**: `report_belief.py` / `report_gated.py` (and `api.py`) load the JSON and render a status/summary; tests assert the aggregation logic across this fixture.

The near-linear timing chain (`propose` end = `accept` start = `completed_at` = `updated_at`, all `18:03:31`) shows the steps are **sequential, not parallel**, and the report is finalized immediately after the last step.

## Invariants

A developer must preserve these when generating or validating the file:

1. **Summary mirrors steps** (hard invariant):
   - `summary.entries (17) == steps[propose].counts.entries (17)`
   - `summary.proposed (260) == steps[propose].counts.proposed (260)`
   - `summary.accepted (78) == steps[accept].counts.accepted (78)`
   - `summary.total_beliefs (201) == steps[accept].counts.total_beliefs (201)`
2. **Chained timestamps**: `steps[i+1].started_at == steps[i].completed_at` (`18:03:31` chaining both boundaries). Steps are chronological and contiguous.
3. **Monotonic clock**: `started_at ≤ updated_at ≤ completed_at`, with `updated_at == completed_at` only after completion.
4. **Status consistency**: if top-level `status == "completed"`, every step's `status` is `"completed"`; conversely an overall `"failed"` should be traceable to a specific step's status/detail.
5. **Detail encodes counts**: the free-form `detail` strings numerically agree with `counts` (`"proposed 260 from 17 entries"`, `"accepted 78 beliefs"`) — a consistency check tests may exploit.
6. **Terminal artifact**: `total_beliefs` is the post-acceptance belief base, so `total_beliefs - accepted` gives the pre-run count (123 here). Downstream cost/reporting code reads it as an absolute, not a delta.
7. **Ordered `steps`**: `steps[0]` is proposal, `steps[1]` acceptance. Readers keying by name must not assume length.

## Error Handling

- **No error state in this file** because this run succeeded (`status: "completed"`, both steps completed). The schema's error surfacing is **data-driven**: a failed run would presumably set top-level `status: "failed"`, the failing step's `status: "failed"`, and a diagnostic in `detail` (or additional fields), rather than throwing.
- **No exceptions from the file itself.** Parsing/validation errors originate in consumers — a malformed or missing `.forge/report.json` would raise `json.JSONDecodeError` / `FileNotFoundError` in `reasons_lib/report_belief.py` or `report_gated.py` (which is why `tests/test_report_belief.py` and `test_report_gated.py` exist to lock down the shape).
- **Silent partial-write window**: `updated_at` exists separately from `completed_at`, so consumers can distinguish an in-progress report from a finished one (or a crash mid-write) via `status != "completed"` / `updated_at != completed_at`. Consumers should not assume `summary` is present while `status == "running"`.
- **Schema drift risk**: because `counts` is per-stage, a reader that assumes `counts.accepted` exists on `propose-beliefs` (or vice-versa) will `KeyError`. Defensive readers should guard on step `name`.

## Beliefs

- `report-json-is-a-runtime-artifact` — `.forge/report.json` is generated pipeline output (not source) written under `.forge/`, and consumers must tolerate it being absent or mid-write.
- `summary-counts-mirror-step-counts` — Every numeric field in `summary` (entries, proposed, accepted, total_beliefs) equals the corresponding value in `steps[].counts`, so the two blocks must be updated together.
- `diary-update-steps-are-sequential` — `steps[1].started_at` equals `steps[0].completed_at` (18:03:31), enforcing strict sequential stage ordering in the report.
- `report-json-is-consumed-by-report-modules` — `reasons/api.py`, `reasons_lib/report_belief.py`, and `reasons_lib/report_gated.py` read this file's schema; renaming keys is a breaking change for them.
- `step-counts-shape-varies-by-name` — `counts` is stage-specific (`{entries, proposed}` for `propose-beliefs` vs `{accepted, total_beliefs}` for `accept-beliefs`), so readers must discriminate by `name` before accessing fields.
