# `.claude/skills/reasons/SKILL.md`

## Purpose

This file is a **Claude Code skill definition** — it is not application code. It lives in the `.claude/skills/` directory and instructs an AI agent (Claude) on *how to use* the `reasons` CLI tool when working inside the `ftl-reasons` repository. Its responsibility is to:

1. **Gate tool access** — the `allowed-tools` field in the YAML frontmatter restricts the agent to only `Bash(reasons *)`, `Bash(cd * && uv run reasons *)`, `Bash(uvx *reasons*)`, `Read`, `Grep`, and `Glob`. No arbitrary shell commands, no Python interpreter, no writes outside `reasons` invocations.
2. **Encode operational knowledge** — it translates the `reasons` tool's semantics (retraction cascades, SL justifications, outlists, nogoods, challenge/defend) into a form an LLM can act on without reading the Python source.
3. **Define workflows** — it prescribes concrete command sequences for common scenarios (init → add → retract → assert, import → status → explain, challenge → defend → re-challenge).

In the project's architecture, this file sits at the **agent-tool boundary**: the `reasons/` package (and its mirror in `reasons_lib/`) is the implementation, and this file is the *contract* the AI agent follows when driving that implementation.

### Body Sections

- **"When to Use `reasons` vs `beliefs`"** — a decision table that disambiguates this tool from the sibling `beliefs` CLI. Key discriminator: dependency density (0.00 flat vs 0.74+ dense) and staleness semantics (source-file change vs upstream retraction).

- **"How to Run"** — a three-step fallback chain for executing the CLI. This is the only "error handling" in the file: try installed → try `uv run` from repo → try `uvx`.

- **"Key Concepts"** — the domain vocabulary (Premise, SL justification, Outlist, Nogood, Challenge/Defend) defined in prose. These map to classes/functions in `reasons/` (e.g., `network.py`, `derive.py`, `contradictions.py`, `review.py`).

- **"Subcommand Behavior"** — one subsection per CLI verb, each specifying:
  - The exact `reasons <verb> …` invocation
  - Expected side effects (cascade, restoration, audit log entry)
  - When to use it vs. an alternative verb

- **"Common Workflows"** — composable sequences. Notably the **dialectical argumentation** workflow (challenge → defend → re-challenge) which maps to `reasons/review.py` and `reasons/review_justifications.py`.

- **"After Any Command"** — post-action reporting rules. This is a *behavioral contract* on the agent: after `retract`, always report cascade scope; after `nogood`, report which premise was backtracked to.

- **"Storage"** — states the backing store is SQLite (`reasons.db`), not markdown. The `--db` flag overrides path.

## Patterns

1. **Skill-as-DSL**: The file is structured as a declarative instruction set, not imperative code. The "code" the agent executes is the `reasons` CLI; this file is the *prompt-level program* that drives it.

2. **Fallback execution chain**: The three-step "try these in order" pattern is a resilience idiom. It mirrors how the Python package's `pyproject.toml` defines both an installable tool (`uv tool install -e`) and a library (`uvx --from ftl-reasons`), so the skill covers all three installation topologies.

3. **Separation of `reasons/` and `reasons_lib/`**: The repo contains two parallel packages. The skill file doesn't reference either directly — it only references the *CLI binary* `reasons`. The agent never needs to know which package the binary resolves to.

4. **Generated-artifact convention**: `export-markdown` produces `beliefs.md` as a *read-only snapshot*. The skill explicitly states: *"operate through `reasons`, not by editing the markdown."* This mirrors the broader project pattern where SQLite is the source of truth and markdown is a projection.

5. **Dialectical symmetry**: `challenge`/`defend` are inverse operations. The skill documents multi-level chains (challenge the defense, defend the defense), which maps to the recursive structure in `reasons/review.py`.

## Flow

Since this is a static instruction document, "execution flow" means the *sequence the agent is told to follow*:

```
Agent receives user intent
  │
  ├─ Identify verb (from argument-hint)
  ├─ Select execution strategy (1 → 2 → 3 fallback)
  ├─ Construct `reasons <verb> <args…>` command
  ├─ Execute via Bash (within allowed-tools)
  ├─ Parse stdout for cascade/reporting
  ├─ Apply "After Any Command" reporting rules
  └─ (If cascade occurred) optionally run `reasons status` / `reasons explain`
```

For multi-step workflows (e.g., "evidence invalidates a foundation"):
```
retract observation-1
  → network.py propagates cascade (SQLite transaction)
  → stdout reports: "retracted observation-1; cascaded: conclusion-1"
  → agent reports cascade to user
  → agent suggests `reasons status`
  → (if user asks) agent runs `reasons explain conclusion-1`
```

The **data flow** inside the tool (invisible to this file but implied) is:
`cli.py` (argparse) → `storage.py` (SQLite read) → `network.py` (propagation) → `storage.py` (SQLite write, ACID) → `cli.py` (format stdout).

## Invariants

These are rules the skill *enforces on the agent's behavior*:

1. **Cascade completeness**: After `retract`, the agent must *not* manually retract dependents. The cascade is atomic (SQLite ACID). The skill states: *"Do not manually retract dependents — the cascade handles it."*

2. **`assert` ≠ `convert-to-premise`**: `assert` only flips a node to IN; it does not remove SL justifications. If a node's justification is structurally invalid (contextual dependency from `import-beliefs`), `assert` alone will revert on next recomputation. The skill explicitly warns: *"reasons assert alone is NOT sufficient for this."*

3. **Source of truth is SQLite**: `export-markdown` output is a projection. The agent must never edit `beliefs.md` directly and expect the DB to reflect it.

4. **Nogood backtracking targets premises, not arbitrary nodes**: The `nogood` command uses dependency-directed backtracking to find the *responsible premise* (fewest dependents = minimal disruption). The agent should report *which premise* was retracted, not just "one node went OUT."

5. **Allowed-tools boundary**: The agent can only execute `reasons *` commands, `cd * && uv run reasons *`, `uvx *reasons*`, and read/grep/glob. No `python -c`, no direct `sqlite3` access, no file writes beyond what `reasons` itself does.

## Error Handling

Error handling in this file is *procedural* rather than *exceptional*:

- **Execution fallback**: If `reasons` is not on PATH, try `cd ~/git/ftl-reasons && uv run reasons …`. If that fails (no repo checkout), try `uvx --from ftl-reasons reasons …`. The agent is told to "try these in order until one works."

- **`check-stale` exit code**: The skill notes `check-stale` "exits 1 if any stale nodes found." This is a CI-friendly contract — the agent (or a workflow in `.github/workflows/`) can branch on `$?`.

- **Cascade reporting**: After `retract` or `nogood`, the agent is required to report *what cascaded*. This is the "error surface" — the agent must surface the blast radius rather than silently succeeding.

- **No explicit error-recovery instructions**: The skill does not define what to do if `reasons add` fails (e.g., duplicate node ID, invalid SL antecedent). Those are handled by the CLI's own argparse/validation in `reasons/cli.py` and surfaced as non-zero exit + stderr.

- **`import-beliefs` caveat**: The skill documents a known limitation (contextual vs. logical dependencies) and prescribes the fix (`convert-to-premise`). This is a *known-bug workaround* encoded as a workflow step.

## Beliefs

- `skill-restricts-agent-to-reasons-cli` — The `allowed-tools` field in the YAML frontmatter is the sole security boundary; the agent cannot execute arbitrary Bash, access `sqlite3` directly, or write files outside what the `reasons` binary produces.
- `assert-does-not-remove-justifications` — `reasons assert node-id` flips a node to IN but preserves its SL justifications; the node will revert to OUT on the next `propagate` if its antecedents are OUT, making `convert-to-premise` the correct fix for structurally-invalid dependencies.
- `export-markdown-is-projection-not-source` — The `reasons export-markdown` output is a read-only snapshot; the skill mandates that all mutations go through the CLI, never through editing the generated markdown file.
- `nogood-backtracks-to-premise-not-arbitrary-node` — The `nogood` command's dependency-directed backtracking always selects the *premise* (node with no justifications) with the fewest dependents for retraction, never an intermediate justified node.
- `skill-file-is-not-importable` — `.claude/skills/reasons/SKILL.md` is consumed exclusively by the Claude Code agent runtime; no Python module in `reasons/` or `reasons_lib/` imports or parses this file.
