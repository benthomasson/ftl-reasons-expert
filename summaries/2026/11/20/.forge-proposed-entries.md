# `.forge/proposed-entries.json`

```json
{
  "entries/2026/04/23/reasons_lib-__init__.md": "9a70f072a5d29dbd",
  ...

```

## 1. Purpose

This is a **staging manifest / index file**, not source code. It is a flat JSON object with exactly **17 entries** (lines 2–18), mapping a *proposed wiki article path* → a *content digest*.

It is the hand-off artifact between two phases of the "forge" pipeline that appears throughout this repo:

1. **Discovery + drafting** — something walks `reasons_lib/` (and other sources), decides which symbols deserve an article, renders Markdown, and hashes it. That phase emits this file plus the richer `.forge/report.json` (the sibling file in the same directory).
2. **Application / sync** — a later step reads this manifest, compares each digest against what is already on disk at `entries/...`, and writes/updates/skips accordingly.

Note that **none of the `entries/...` paths exist in this working tree** — the tree only has `.forge/proposed-entries.json` and `.forge/report.json`. That is the whole point: these are *proposals*. The manifest is declarative ("here is what the wiki should look like and what bytes it should contain"), and idempotent-by-hash. It owns **no** logic — its responsibility is purely to be a durable, diffable record of *intent*.

## 2. Key Components

There are no classes or functions. The "components" are the key/value conventions, which are strict enough to be an API:

### Key grammar

```
entries/YYYY/MM/DD/<slug>.md
```

- **Date partition** — every key is under `entries/2026/04/23/`. Uniform across all 17 entries, so today's batch is a single partition. This is a date-sharded wiki layout (one directory per day of ingestion), which keeps directory listings bounded and makes "what changed on this date" a `ls`.
- **`<slug>` is derived from a source coordinate**, with `/`, `.`, and `:` flattened to `-` while **underscores are preserved**:

| Slug | Source coordinate |
|---|---|
| `reasons_lib-__init__` | module `reasons_lib/__init__.py` |
| `reasons_lib-api` | module `reasons_lib/api.py` |
| `reasons_lib-network` | module `reasons_lib/network.py` (umbrella article) |
| `reasons_lib-network-challenge` | `reasons_lib/network.py:challenge` |
| `reasons_lib-network-add_nogood` | `reasons_lib/network.py:add_nogood` |
| `reasons_lib-network-_propagate` | `reasons_lib/network.py:_propagate` |
| `reasons_lib-network-_justification_valid` | `reasons_lib/network.py:_justification_valid` |
| `reasons_lib-check_stale-check_stale` | `reasons_lib/check_stale.py:check_stale` |

Two consequences worth internalizing:

- **Private helpers are in scope.** `_propagate` and `_justification_valid` both get their own entry. The scope filter is *not* "public API only" — it is apparently "symbols that carry the interesting algorithmic load." Those two are precisely the propagation/fixpoint core of a truth-maintenance system (see `reasons/merkle.py`, nogoods, challenges).
- **Module and member share a prefix**, so `reasons_lib-network.md` is an umbrella page and the four `reasons_lib-network-*.md` are its children. Note the umbrella sorts *after* its children in the file (`...network-_justification_valid`, `...network-_propagate`, `...network-add_nogood`, `...network-challenge`, `...network`), because `-` (0x2D) < `.` (0x2E) in ASCII. That is a clean fingerprint of the producer doing a plain `sorted()` on the joined path string rather than a structured sort. Don't "fix" this ordering casually — a downstream diff-consistency check may depend on it.

### Non-code-derived entries

Three entries have no module behind them, which tells you the pipeline has more than one source:

- `scan-ftl-reasons.md` — a **scan/overview** article (the `ftl-reasons` label suggests the project's own codename; "FTL" as in forward/truth-maintenance layer).
- `topic-doyle-1979-tms.md` — literature note (Doyle's 1979 truth-maintenance-system paper, the canonical citation for the justification/nogood model used in `reasons/network.py`).
- `topic-multi-agent-federation.md`, `topic-outlist-semantics.md` — conceptual articles. `outlist` matches `tests/test_outlist.py`, and "nogood"/"outlist" is the standard TMS vocabulary for recording *defeated* justifications.

So the slug namespace is **not** free-form: it is one of `reasons_lib-*`, `scan-*`, or `topic-*`. A new prefix is a schema change.

### Value domain

Every value is **exactly 16 lowercase hex characters** = 64 bits:

```
9a70f072a5d29dbd   be57ef94e9958794   22ae106efee43f3b   ...
```

64 bits is a *short* digest — this is change detection / content addressing, **not** integrity or security. It matches a truncated `hashlib` digest (e.g. `sha256(...).hexdigest()[:16]`). The relevant sibling is `reasons/merkle.py` / `reasons_lib/merkle.py` / `tests/test_merkle.py`: this repo already has a Merkle/stability-hash concept, and this manifest is a one-level Merkle root over the entry set (root = deterministic map of leaf → leaf hash, no separate root field needed because the map itself is sorted and diffable).

## 3. Patterns

- **Content-addressed manifest (a lockfile for docs).** The digest lets the applier answer "is this article already byte-identical?" without reading/parsing Markdown. Same role as `package-lock.json` integrity hashes or a Bazel action cache key.
- **Propose-then-apply (two-phase commit against the filesystem).** `.forge/proposed-entries.json` is the *plan*; writing into `entries/` is the *apply*. The plan is inspectable and reviewable in a PR before anything is materialized — presumably why it lives in a dot-directory under version control at all.
- **Date-sharded keys.** `entries/YYYY/MM/DD/` — avoids one giant directory, gives free time-travel semantics, and makes re-runs on a different day non-destructive (they propose a new partition rather than mutating yesterday's).
- **Deterministic serialization.** 2-space indent, one key per line, keys sorted lexicographically as full path strings, trailing newline. The file is designed to produce a *minimal, meaningful* `git diff`: one added line = one proposed article. Never reformat it with a different indenter or key order or you'll create a 17-line diff for a 1-entry change.
- **Flat dictionary, no envelope.** No `version`, no `generatedAt`, no `root` field. The timestamp is encoded *in the keys* (`2026/04/23`). This is deliberate minimalism, but it means the file has **no schema version** — see invariants/risks below.

## 5. Flow

```
walk sources ──► select targets ──► render Markdown ──► hash[:16] ──► sorted dict ──► .forge/proposed-entries.json
   (reasons_lib/,     (modules,        (template)         (merkle)        (lexicographic)          │
    topics, scans)     functions,                                                                    ▼
                       private _helpers)                                     compare to existing entries/
                                                                                       │
                                                                        match ──► skip (idempotent)
                                                                        differ/missing ──► write
                                                                                       │
                                                                              .forge/report.json + costs/
```

The transformation this file represents is, per entry: `source coordinate → (slug, digest)`. There is **no** logic here; all of the decision-making happened upstream. Reading it backwards (slug → coordinate) is exactly how you audit "did anything important get skipped?" — and the answer is visibly yes: there are **no** entries for `ask`, `contradictions`, `llm`, `pg`, `verify`, `storage`'s peers, `mcp_server`, etc. Only 10 of ~34 modules appear. That selectivity is the interesting signal; it means the producer applies a significance filter, not a blanket docstring scrape.

## 6. Invariants

1. **All keys share one date partition** (`entries/2026/04/23/`). A manifest spanning two dates implies two runs merged — possible, but check the report.
2. **Every key ends in `.md`** and begins with `entries/`. No absolute paths, no `..` — the applier can safely `join(wiki_root, key)`.
3. **Every value is 16 lowercase hex chars.** Anything else (40 chars, base64, uppercase, `null`) means a different/older hasher.
4. **Keys are unique** — enforced structurally by JSON objects. The flip side: a duplicate key in the source JSON is *silently* collapsed to the last occurrence by any parser, so a bug upstream that proposes the same slug twice would vanish here without an error.
5. **Keys are lexicographically sorted as full strings.** Determinism of the file is a stronger invariant than determinism of the content hash, because it guarantees a stable diff.
6. **Slugs are case-collision-safe and shell-safe**: `[a-z0-9_-]` only. This matters on case-insensitive filesystems (macOS/Windows) — two entries differing only in case would collide on checkout.
7. **Digest must be a pure function of the rendered content.** If the renderer emits a timestamp, run ID, or non-deterministic dict ordering into the Markdown, every run proposes all 17 entries as changed and the manifest becomes useless. This is the single most fragile assumption in the design.
8. **One slug per source coordinate.** The mapping is not many-to-one; `check_stale-check_stale` means module and function share a name and still get a nested slug rather than colliding.

Missing invariants (deliberate risks worth flagging): **no schema version field**, **no `generatedAt`**, **no total/root hash**, **no list of skipped targets**. If the slug grammar changes, old and new manifests are indistinguishable except by inspection.

## 7. Error Handling

There is no runtime error handling in a JSON data file; the semantics are entirely in the producers/consumers:

- **Parse failure is fatal.** A truncated file (e.g. an interrupted write) makes the whole manifest unusable — there is no partial-recovery envelope. Producers should write temp-then-rename. Verify with `python -m json.tool .forge/proposed-entries.json` before committing.
- **Stale digest = abort or regenerate.** If the applier sees `entries/.../reasons_lib-network.md` on disk whose hash ≠ `02393624971b7cf1`, the correct behavior is regenerating that one article, not trusting the manifest's bytes. The manifest is a *cache key*, so a mismatch is a cache miss, never an error.
- **Missing key = nothing to do.** An article on disk absent from this manifest is not orphaned by this file — the manifest has no tombstones/deletions. Deletion must be handled elsewhere (or not at all).
- **Hash collision** is theoretically possible at 64 bits but irrelevant at n=17. Do not treat the digest as a security boundary.
- **Truncated digests lose provenance.** Because only 16 hex chars are kept, you cannot tell *which* algorithm produced it (`sha1[:16]` vs `sha256[:16]` are indistinguishable). If `merkle.py` ever changes hash function, digests will differ and everything will look "changed" once — expected, but confusing. Band-aid: bump the run to a new date partition.
