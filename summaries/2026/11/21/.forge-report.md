# File: .forge/report.json

# `.forge/report.json`

## Purpose

`.forge/report.json` is **not source code — it is a generated run ledger** for the `diary-update` pipeline. It records the lifecycle, per-step outcomes, and aggregate counts of one execution of the belief‑extraction/acceptance workflow.

Its responsibility is **audit/observability**: it answers "when did the last diary update run, which steps ran, in what order, how long did they take, and what did they produce?" It is deliberately machine‑readable so that the reporting layer (`report_belief.py`, `report_gated.py`) and the API surface (`api.py`) can parse it without hardcoding expectations about the pipeline's internals.

The sibling `.forge/proposed-entries.json` supplies the input entries for the run; this report captures the result.

---

## Key Components

### Top‑level envelope

| Key | Value here | Contract |
|---|---|---|
| `pipeline` | `"diary-update"` | Identifies the workflow that produced the report. |
| `started_at` | `2026-11-20T18:00:10+00:00` | ISO‑8601 with explicit UTC offset; must be ≤ `completed_at`. |
| `updated_at` | `2026-11-20T18:00:11+00:00` | Last write timestamp; equals `completed_at` on a finished run. |
| `status` | `"completed"` | Aggregate outcome; drives downstream gating. |
| `completed_at` | `2026-11-20T18:00:11+00:00` | Terminal timestamp for the whole run. |

### `steps[]`

An **ordered** list of step records. Each entry has:

- `name` — canonical step id (`propose-beliefs`, `accept-beliefs`)
- `status` — per‑step outcome (`completed` here)
- `started_at` / `completed_at` — ISO‑8601 timestamps
- `detail` — human‑readable summary string
- `counts` — machine‑readable numeric payload (this is the part consumers should trust)
- `duration_seconds` — derived convenience field

Observed steps:

1. **`propose-beliefs`** — reads `17` diary `entries`, produces `260` `proposed` belief candidates. Detail: `"proposed 260 from 17 entries"`.
2. **`accept-beliefs`** — evaluates candidates against the store: `0` `accepted`, final store size `total_beliefs: 201`. Detail: `"accepted 0 beliefs"`.

### `summary`

A **denormalized aggregate** of the terminal counters:

```json
"entries": 17, "proposed": 260, "accepted": 0, "total_beliefs": 201
```

This is a cache for readers that don't want to walk `steps[]` — its values must equal the corresponding `counts` fields.

## Patterns

- **Run ledger / provenance record.** Structurally similar to a GitHub Actions or Airflow run record: envelope → ordered steps → summary.
- **Denormalized summary.** `summary` intentionally duplicates step counts for O(1) access.
- **Step-typed counts object.** Each step advertises whatever counters are relevant to it (`entries`/`proposed` vs `accepted`/`total_beliefs`).
- **Idempotent overwrite per run.** The file is a single snapshot, not an append log — `updated_at` and `completed_at` are the same on success, and a rerun would overwrite it.
- **Status as a gate flag.** `status` is not just informational — downstream `report_gated.py` is named for *gating* on it, so consumers likely reject/flag a run whose `status` is not `"completed"`.

## Dependencies

**Producer (write side):** the `diary-update` pipeline itself (drawn from `propose_update.py` / `cli.py` orchestration — not visible in this file).

**Consumers (read side)** — from `imported_by`:

- `reasons/api.py` — exposes run status/results programmatically.
- `reasons_lib/report_belief.py` — renders a belief report from the run's counters.
- `reasons_lib/report_gated.py` — gate logic keyed on `status` and `summary`.
- `tests/test_report_belief.py`, `tests/test_report_gated.py` — assert the schema/gating contract.

The file itself has **no imports**: it is pure data. Changing its shape is a *breaking contract* for every one of those readers.

## Flow

1. Pipeline starts, writes/overwrites `.forge/report.json` with `pipeline`, `started_at`, and a non‑terminal `status`.
2. **`propose-beliefs`** iterates the 17 input entries, extracts 260 candidate beliefs, emits a step record with `counts.entries = 17`, `counts.proposed = 260`.
3. **`accept-beliefs`** runs the candidates through whatever acceptance predicate exists (dedupe against the 201 existing beliefs, thresholds, etc.). Result: `accepted = 0`, store still has `total_beliefs = 201`. Emits a step record and its `counts`.
4. `summary` is built from the step `counts`.
5. `status` is promoted to `"completed"`, `completed_at`/`updated_at` are stamped. Readers then consume the file.

**Notable observation:** 260 proposals yielded **0** accepted against a store of **201** beliefs. That is a strong signal the acceptance predicate is highly restrictive (dedupe/threshold/gating) or the run was a dry run. This is exactly what a developer investigating "why didn't the diary update change anything?" should check first.

## Invariants

- **Monotonic timestamps:** `started_at ≤ completed_at` at the envelope and for every step; `duration_seconds` should equal `completed_at − started_at` (both `0.01` here, consistent with the 1‑second envelope delta).
- **Step ordering:** `steps[]` is execution‑ordered — `propose-beliefs` precedes `accept-beliefs`. Consumers may rely on that (e.g., taking `steps[0]` or `steps[-1]`).
- **Summary/step consistency:** `summary.entries == steps[propose].counts.entries`, `summary.proposed == steps[propose].counts.proposed`, `summary.accepted == steps[accept].counts.accepted`, `summary.total_beliefs == steps[accept].counts.total_beliefs`.
- **Terminal status semantics:** `status == "completed"` implies all step statuses are `"completed"` and `completed_at` is present.
- **`total_beliefs` is the post‑run store size**, not `accepted + prior` naively — it reflects the actual store state (201 here), so it is the authoritative number for "how many beliefs exist after this run."

---

## Error Handling

As a data artifact, **errors are recorded, not raised**:

- A failed run would surface as `status != "completed"` (e.g., `"failed"` or `"partial"`), with the offending step carrying the non‑completed status and its `detail` explaining why.
- `report_gated.py` is presumably where a non‑completed status is turned into a user‑visible refusal/error — this file is the *input* to that decision, not the place errors are thrown.
- Readers must tolerate partially populated step objects (e.g., a step with `started_at` but no `completed_at` mid‑run), since the file is written incrementally during execution.
- Since the file is overwritten each run, there is **no history of failed runs** here; any audit of failures must come from logs or a separate store.

## Beliefs

- `report-is-generated-artifact` — `.forge/report.json` is a pipeline run ledger written by the diary-update workflow, not hand-maintained source.
- `report-steps-are-ordered` — `steps[]` preserves execution order, with `propose-beliefs` before `accept-beliefs`.
- `summary-mirrors-step-counts` — `summary.entries/proposed/accepted/total_beliefs` duplicate the corresponding `counts` fields on the step records.
- `duration-seconds-derives-from-timestamps` — Each step's `duration_seconds` equals `completed_at − started_at` (both 0.01s in this run).
- `report-status-completed-enables-gated-publishing` — Downstream `report_gated.py` treats the top-level `status` as a gate; only `completed` runs pass.
