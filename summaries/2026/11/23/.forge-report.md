# File: .forge/report.json

# `.forge/report.json`

## Purpose

This file is **not code** — it is a machine-readable **run report (audit artifact)** emitted by the `diary-update` pipeline. It is the structured record of one end-to-end execution of the belief-extraction pipeline:

1. `propose-beliefs` — read diary entries and generate candidate beliefs.
2. `accept-beliefs` — reconcile candidates against the existing belief store.

It records timing, per-step status, human-readable `detail` strings, numeric `counts`, and a rolled-up `summary`. Downstream consumers (`api.py`, `report_belief.py`, `report_gated.py`) read or write this path to surface "what did the last diary run do?" — it is telemetry, not state.

Crucially, the *state* (`260` proposals) lives in the sibling file `.forge/proposed-entries.json`; `.forge/report.json` only describes the run.

## Key Components (the schema)

There are no functions or constants — the "API" is the JSON contract:

### Top-level fields
| Key | Type | Meaning |
|---|---|---|
| `pipeline` | string | Pipeline identifier, here `"diary-update"`. Used to distinguish report types. |
| `started_at` / `updated_at` / `completed_at` | ISO 8601 string w/ `+00:00` | Run lifecycle timestamps. `updated_at` allows incremental writes; `completed_at` is set only on terminal success. |
| `status` | string | Overall run status (`"completed"` here). |
| `steps` | array | Ordered list of step-report objects. |
| `summary` | object | Denormalized roll-up of the numeric `counts` across steps. |

### Step object (e.g. `steps[0]`)
```
name: "propose-beliefs"
status: "completed"
started_at / completed_at
detail: "proposed 260 from 17 entries"   # human-readable, no structured contract
counts: { entries: 17, proposed: 260 }   # machine-readable
duration_seconds: 0.01
```
`steps[1]` is `accept-beliefs` with `counts: { accepted: 0, total_beliefs: 201 }` and `detail: "accepted 0 beliefs"`.

### `summary`
```
entries: 17, proposed: 260, accepted: 0, total_beliefs: 201
```
This is exactly the union of the per-step `counts` objects — it is derived, not independent.

## Patterns

- **Structured telemetry with a denormalized roll-up.** Each step owns its `counts`; `summary` is a redundant aggregate for cheap querying without iterating `steps`. Consumers must tolerate this duplication.
- **Step-array ordering as execution order.** The pipeline is sequential; `steps` is ordered (`propose-beliefs` before `accept-beliefs`), so consumers can rely on index, not just `name`.
- **Human + machine dual channel.** Every step has both `detail` (free text for logs/UI) and `counts` (stable keys for code). Never parse `detail`.
- **Idempotent-looking timestamps.** All timestamps are identical and durations are `0.01` — strongly suggests a **mocked clock / deterministic fixture**, likely produced or normalized by tests (`tests/test_report_belief.py`, `tests/test_report_gated.py`). Treat timing fields as unreliable for benchmarking.
- **Report-vs-artifact separation.** Proposals are staged in `.forge/proposed-entries.json`; the report merely counts them. `accepted: 0` does not mean nothing was proposed — it means nothing was *merged*.

## Flow

1. Pipeline starts → writes `started_at`, `status` (probably `"running"`), `updated_at`.
2. `propose-beliefs` executes: reads 17 entries → emits 260 candidates → appends a step object with `counts.entries=17`, `counts.proposed=260`.
3. `accept-beliefs` executes: loads existing store (201 beliefs) and the staged proposals → accepts 0 → appends step with `counts.accepted=0`, `counts.total_beliefs=201`.
4. Pipeline finalizes: computes `summary` from step `counts`, sets `status="completed"` and `completed_at`, rewrites file.

The observed relationship — `260` proposed but only `201` total beliefs, and `0` accepted — confirms the two numbers measure different things: `proposed` is a candidate count, `total_beliefs` is the current store size.

## Invariants

These are the rules the writers and the tests enforce:

- **`steps` order is fixed**: `propose-beliefs` precedes `accept-beliefs`.
- **`summary` mirrors step `counts`**: `summary.entries == steps[propose].counts.entries`, `summary.proposed == steps[propose].counts.proposed`, `summary.accepted == steps[accept].counts.accepted`, `summary.total_beliefs == steps[accept].counts.total_beliefs`.
- **`status == "completed"` ⇒ `completed_at` is present**, and every step is also `"completed"`. A failed/partial run would presumably have `"failed"`/`"partial"` and a null `completed_at`.
- **`0 ≤ accepted ≤ proposed`** and **`accepted ≥ 0`** (accepted `0` here, within bounds).
- **`total_beliefs` is independent of `proposed`** — it may be smaller (201 < 260) without violating anything.
- **Timestamps are ISO 8601 with explicit `+00:00` offset** — consumers can parse without assuming local time.
- **Every step carries `name`, `status`, `counts`, `detail`, and `duration_seconds`** — a stable shape.
- **`accepted == 0` does not imply the run did nothing** — proposals may still be staged.

## Error Handling

Since this is data, "error handling" means the semantics the reader must respect:

- **Terminal status is encoded in `status`, not exceptions.** A failed step does not raise — it flips `status` and likely leaves `completed_at` null / `detail` populated with a reason. Consumers must branch on `status`/`completed_at`, not on missing fields.
- **`detail` is the only place a human-readable failure reason would appear** (there is no `error` field in this instance). If you need structured errors, check `report_gated.py` / `report_belief.py` for whether they add an `errors` array on failure — the completed run here has none.
- **`updated_at` enables partial writes.** A crash mid-run leaves `updated_at < completed_at`-style inconsistency; treat a report as valid only when `status == "completed"`.
- **Silent acceptance of nothing.** `accepted: 0` is a *success*, not an error — the pipeline completed with zero merges. Do not treat zero as failure.

## Beliefs

- `report-json-summary-maps-to-step-counts` — Every `summary` field (`entries`, `proposed`, `accepted`, `total_beliefs`) equals the corresponding `counts` value in the `steps` array, making `summary` a derived denormalization.
- `report-json-status-completed-implies-completed-at` — When the top-level `status` is `"completed"`, the `completed_at` field is present and non-null.
- `report-json-steps-order-propose-before-accept` — The `steps` array orders `propose-beliefs` before `accept-beliefs`, reflecting sequential pipeline execution.
- `report-json-timestamps-are-utc-iso8601` — All timestamps use ISO 8601 with an explicit `+00:00` UTC offset.
- `report-json-accepted-is-independent-of-proposed` — In this run `proposed` (260) exceeds `accepted` (0) and `total_beliefs` (201), so the four summary counts are not constrained to be monotonic with each other.
