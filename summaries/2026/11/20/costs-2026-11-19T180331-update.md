## 1. Purpose

- **Cost auditability** — capture `calls`, `input_tokens`, `output_tokens`, and `cost_dollars` so spend can be reconciled per-operation and per-model.

## 3. Patterns / idioms

- **Append-only event log.** Filename = `<ISO-timestamp>-<operation>.json`. Every run is a new file; nothing is overwritten. This is the classic "one immutable event per file" pattern that keeps concurrent writers from clobbering each other.
- **Aggregate + breakdown duplication.** `cost_dollars`, `calls`, and the token sums are redundantly derivable from `by_model`. That redundancy is deliberate: it lets cheap consumers read a single scalar without walking the map, and it lets reconciliation checks detect drift.
- **Snapshot-like record.** It captures the state *around* an operation (`beliefs_*`) plus the resource *of* the operation (`calls`, tokens) in one document — the "run manifest" idiom.
- **Structured operation code.** `operation` is an enum-like short string rather than free text, so filenames and logs can be filtered/grepped by stage.

## 5. Flow

1. An `update` operation begins (e.g., ingest sources → derive candidate beliefs → import them).
2. Each LLM call is wrapped by `reasons/llm.py`, which accumulates `(calls, input_tokens, output_tokens, cost)` per model.
3. When the operation finishes, the belief store is diffed to compute `beliefs_added`, `beliefs_retracted`, `beliefs_unchanged`.
4. A writer serializes the totals + `by_model` map to `costs/<timestamp>-update.json`.
5. Downstream tooling globs `costs/*.json`, groups by `operation`/`model`/day, and produces spend reports.

## 6. Invariants

A maintainer should treat these as rules any *correct* file in `costs/` obeys (and any writer must enforce):

- **Filename ↔ timestamp.** `<YYYY-MM-DDTHHMMSS>-<operation>.json` must match `timestamp` (modulo separators) and `operation`.
- **Aggregate = sum of parts.** `cost_dollars == Σ by_model[*].total_cost_usd`; `calls == Σ by_model[*].calls`; `input_tokens == Σ by_model[*].input_tokens`; likewise output. In this file all sums trivially hold (single model, zero cost).
- **`model` is a key in `by_model`.** The headline model should appear as an entry in the breakdown.
- **Non-negative counters.** All numeric fields are ≥ 0; token counts are integers.
- **`cost_dollars == 0.0` is legal**, not an error — it signals an unpriced/free endpoint rather than a failed run.
- **Belief deltas are independent of cost** — an update can cost tokens and change zero beliefs (as here), or change beliefs with no LLM calls (pure repairs). Don't infer success/failure from the counters alone.

## 7. Error Handling

There is no executable error handling in a JSON artifact, but the schema implies where failures surface:

- An **aborted / failed** update would most plausibly be recorded as a different `operation` value or omitted entirely — this schema has no `error`/`status` field, so a partial run that still writes the file will look "successful."
- Because tokens and cost are reconciled by summation, a bug in `reasons/llm.py`'s accounting shows up as a **mismatch between aggregate and `by_model`**, not a raised exception. Consumers should validate the sum invariant when reading.
- A **malformed filename** (timestamp mismatch) is not caught by the JSON parser at all — it's a naming-convention concern, so file-discovery tooling should parse the name defensively.
