# File: .forge/report.json

# `.forge/report.json` — Pipeline Run Report

This is **not source code** — it is a **persisted runtime artifact**. It is a JSON snapshot of the last execution of the `diary-update` pipeline, written into the `.forge/` directory so it can be consumed by the reporting/CLI layers and asserted against by tests.

---

## 1. Purpose

`.forge/report.json` is the **machine-readable journal of the most recent `diary-update` pipeline run**. Its responsibility is to answer, without re-running anything:

- *Did the run finish?* (`status`, `completed_at`)
- *How long did it take?* (`started_at` → `completed_at`, per-step `duration_seconds`)
- *What happened in each phase?* (`steps[]`, each with `name`, `status`, `counts`, `detail`)
- *What was the net effect?* (`summary.entries`, `summary.proposed`, `summary.accepted`, `summary.total_beliefs`)

It is a **provenance / observability artifact**, not configuration and not a data store. The actual belief store lives elsewhere (the 201 `total_beliefs` are only *reported* here, not held here). The sibling `.forge/proposed-entries.json` likely holds the intermediate payload that `propose-beliefs` produced, while `report.json` holds only the *outcome metrics* of that phase.

Because `reasons/api.py`, `reasons_lib/report_belief.py`, and `reasons_lib/report_gated.py` all reference it, this file is part of the public surface for the "report" feature — a consumer can load it to render a status summary, gate a release, or show a CI badge.

## 2. Key Components (JSON schema)

| Field | Type | Contract |
|---|---|---|
| `pipeline` | string | Stable identifier of the pipeline that produced the run (`"diary-update"`). Used by consumers to decide whether the report is relevant. |
| `started_at` | RFC 3339 string | Pipeline start. Timezone-offset required (`+00:00` here). |
| `updated_at` | RFC 3339 string | Last write. Distinguishes a *stale in-progress* report from a finished one. |
| `completed_at` | RFC 3339 string | Present only when `status == "completed"`; absent/null while running. |
| `status` | enum | `"running" | "completed" | "failed"` (inferred). Top-level status is a rollup of step statuses. |
| `steps[]` | array | Ordered, append-only list of step records. |
| `steps[].name` | string | Step identifier (`propose-beliefs`, `accept-beliefs`). Must be unique within a report — consumers key off it. |
| `steps[].status` | enum | Same enum as top-level, scoped to the step. |
| `steps[].detail` | string | Human-readable, free-form. **Do not parse** — it duplicates `counts` in prose (`"proposed 260 from 17 entries"`). |
| `steps[].counts` | object | Step-specific metric bag. Keys are **not** standardized across steps (`entries`/`proposed` for one, `accepted`/`total_beliefs` for another). |
| `steps[].duration_seconds` | number | Wall-clock duration, rounded to 2 dp here. |
| `summary` | object | Denormalized flattening of the per-step `counts` into run-level totals. |

Note the `counts` asymmetry: `propose-beliefs` owns `entries` and `proposed`; `accept-beliefs` owns `accepted` and `total_beliefs`. The `summary` object is the **union** of those keys, so consumers should read `summary` when they want a run-level view and `steps[].counts` only for per-phase detail.

Two facts are worth calling out because they look like anomalies but are actually meaningful:

- **`proposed: 260` but `total_beliefs: 201`.** The pipeline proposed more beliefs than exist in the store afterward. That is only possible because `accepted: 0` — the *accept* phase gated out every proposal this run (likely blocked by `report_gated.py`'s gating rules, or a dry-run/review state).
- **All timestamps equal `18:00:06` and `duration_seconds: 0.01`.** The propose step turned 17 entries into 260 proposals in 10 ms — far too fast for per-belief LLM calls. The proposal path here is deterministic/rule-based, or the run is a replay.

## 3. Patterns

- **Append-only step log.** `steps[]` is an ordered event list; a report is finalized by appending, never by rewriting earlier entries. This makes it safe to sample mid-run.
- **Denormalized summary.** `summary` is intentionally redundant so a single load gives the run-level answers without walking `steps[]`. This trades a tiny write-time cost for read-time simplicity.
- **Status rollup.** Top-level `status` and `completed_at` are derived from step statuses. A failed late step leaves the top-level status non-`completed`.
- **Human + machine dual channel.** `detail` (prose, for logs/humans) sits next to `counts` (structured, for code). Consumers must prefer `counts`.
- **File-as-interface.** No Python import; `imported_by` means these modules *read this path*. The schema is the contract. This is the same pattern as `.forge/proposed-entries.json` and `costs/*.json`.

## 5. Flow

**Write path (pipeline):**
1. Run begins → write `{pipeline, started_at, updated_at, status: "running", steps: []}`.
2. `propose-beliefs` completes → append a step record with `counts: {entries, proposed}` and `duration_seconds`.
3. `accept-beliefs` completes → append a step record with `counts: {accepted, total_beliefs}`.
4. Finalize → set top-level `status`, `completed_at`, and flatten step counts into `summary`.

**Read path (consumers):**
1. `report_belief.py` loads the JSON (probably tolerating a missing file for first-run).
2. It selects the top-level `status`/`summary` for display.
3. `report_gated.py` applies gate rules — e.g. only pass if `status == "completed"`. In this snapshot the gate sees `accepted: 0`, which likely means "no changes to publish".
4. `api.py` serializes the loaded structure outward.

**Data transformation:** per-step `counts` → merged into `summary`; timestamps → durations. No derived fields beyond that.

## 6. Invariants

- **Temporal ordering:** `started_at <= updated_at <= completed_at`; every `steps[i].started_at <= steps[i].completed_at`. This snapshot trivially satisfies it (all equal).
- **Completion implies `completed_at` present:** `status == "completed"` ⟹ `completed_at` non-null and top-level `completed_at` set.
- **Step-name uniqueness:** `steps[].name` values are unique within a report; consumers index by name.
- **Summary mirrors steps:** every key in a step's `counts` appears in `summary` (union), and `summary.values` equal the corresponding step values. Here: `17`, `260`, `0`, `201` line up exactly with the two steps.
- **`total_beliefs` is a store-level count, not a delta** — it is not `proposed - accepted`. Do not derive it.
- **`detail` is not a contract.** Tests must assert on `counts`/`summary`, never on prose parsing.
- **`pipeline` is stable** across runs of the same pipeline; consumers filter on it.

## 7. Error Handling

This is a data file, so "error handling" is about how *producers and consumers* treat it:

- **Missing/empty file** — the reader (`report_belief.py`) is expected to handle first-run absence gracefully (otherwise every fresh checkout would crash the CLI). Treat a missing file as "no report yet", not an exception.
- **Malformed JSON** — no recovery is possible inside the file; this surfaces as a `JSONDecodeError` in the loader and is a test failure / hard error, since a corrupt report indicates an interrupted write.
- **Interrupted run** — the writer's `status: "running"` + stale `updated_at` is the failure signal. There is no separate `error` field in this schema, so **step failure is encoded only as `status: "failed"` plus an optional `detail` message**. Consumers that need error text must read `detail`.
- **Gate outcomes are not exceptions** — `accepted: 0` is a *successful* completed run that accepted nothing. `report_gated.py` must distinguish "gate rejected everything" from "gate errored"; here the report says success, so the gate should treat 0 as a valid no-op, not a failure.
- **Atomicity** — writes should be atomic (write-temp-then-rename) so readers never observe a truncated JSON document. Nothing in the file enforces this; it's a writer obligation.
