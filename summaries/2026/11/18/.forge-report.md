# File: .forge/report.json

# `.forge/report.json` — diary-update run report

## Purpose

`.forge/report.json` is not source code — it is a **machine-readable run ledger** for a pipeline named `diary-update`. It records what happened during the most recent execution of that pipeline: when it started, which stages ran, how many items each stage processed, and the aggregate result.

Its responsibility is *observability and reproducibility of a single run*, not business logic. It exists so that:

- `reasons/api.py` can expose the last run's outcome without scraping logs,
- `reasons_lib/report_belief.py` and `reasons_lib/report_gated.py` can render human-facing reports about proposals/acceptance,
- tests (`tests/test_report_belief.py`, `tests/test_report_gated.py`) can assert on the report shape and counts.

It is a sibling of `.forge/proposed-entries.json` (upstream proposals) and is the canonical, single-location artifact for "the last diary update" — unlike `costs/<timestamp>-update.json`, which is timestamped and append-style. This file is overwritten per run.

## Key Components

The file is one JSON object representing one run. There are three nested "components":

### 1. Run envelope (top-level fields)

| Field | Meaning / contract |
|---|---|
| `pipeline` | String identifier of the orchestrator: `"diary-update"`. Consumers switch on this to know which schema to expect. |
| `started_at`, `updated_at`, `completed_at` | ISO-8601 timestamps with explicit UTC offset (`+00:00`). `started_at` is set when the run begins; `updated_at` is touched as steps finish; `completed_at` is set only on terminal success. |
| `status` | Run-level lifecycle enum. Here `"completed"`. Presumably also `"running"` / `"failed"` in other runs. |
| `steps` | Ordered array of step records. Order is meaningful — it is pipeline stage order, not alphabetical. |
| `summary` | Denormalized aggregate counters, derived from the steps for cheap reads. |

### 2. Step records (`steps[]`)

Each entry is a per-stage record:

| Field | Meaning / contract |
|---|---|
| `name` | Stage identifier: `"propose-beliefs"`, `"accept-beliefs"`. These are the pipeline's ordered stages. |
| `status` | Per-step lifecycle enum. Here `"completed"` for both. |
| `started_at`, `completed_at` | Step-local timestamps, same format as the envelope. `completed_at` should be `>= started_at`. |
| `detail` | Human-readable, *non-authoritative* string (`"proposed 182 from 17 entries"`, `"accepted 0 beliefs"`). |
| `counts` | Step-specific integer counters. **Schema varies per step** — see below. |
| `duration_seconds` | Float wall-clock duration, measured independently of the second-resolution timestamps. |

Step-specific counters in this run:

- `propose-beliefs.counts = { entries: 17, proposed: 182 }`
- `accept-beliefs.counts  = { accepted: 0, total_beliefs: 123 }`

### 3. Summary (`summary`)

```json
{ "entries": 17, "proposed": 182, "accepted": 0, "total_beliefs": 123 }
```

This is a projection of the step counts: `entries`/`proposed` come from the propose step; `accepted`/`total_beliefs` come from the accept step. It is redundant by design so report consumers do not have to walk `steps`.

### The run this file captures

- 17 diary entries were read.
- 182 beliefs were proposed (≈10.7 per entry, consistent with an LLM-extraction stage).
- 0 of those 182 were accepted.
- The belief store ended with 123 beliefs (unchanged, since nothing was accepted).
- Both steps and the whole run are `"completed"`.

The fact that `accepted` is `0` while `proposed` is `182` is the most operationally significant number here: the acceptance stage is **gated** (see `report_gated.py`), and in this run nothing passed the gate. The pipeline still reports `"completed"` — "zero accepted" is a valid outcome, not an error.

## Patterns

- **Run ledger / pipeline telemetry artifact.** A JSON sidecar next to the data it describes (`.forge/`), consumed programmatically rather than by humans.
- **Ordered step list (append-style within a run).** `steps` preserves execution order; producers append as stages finish. Combined with `updated_at`, this supports a "live progress" read while the pipeline is running.
- **Denormalized summary view.** `summary` duplicates step counts to give consumers a stable top-level shape regardless of how many steps the pipeline grows.
- **Two-level status.** Run status plus per-step status, allowing partial-failure reporting.
- **Gating.** The `accept-beliefs` stage is a filter/gate whose accepted count can legitimately be zero; `report_gated.py` is the corresponding reporter.
- **Second-resolution UTC ISO-8601 timestamps + float durations.** Timestamps are for ordering/display; `duration_seconds` is the precise timing signal. In this run all four timestamps are identical (`2026-11-18T18:00:09+00:00`), which is expected when the whole run finishes within the same second.
- **Single canonical path.** Latest run overwrites `.forge/report.json`; historical runs are not retained here (contrast with `costs/<timestamp>-update.json`).

## Flow

The filename and stages imply this control flow for `diary-update`:

1. Orchestrator (in `api.py` / `propose_update.py`) initializes `.forge/report.json` with `pipeline: "diary-update"`, `status: "running"` (not shown in this final snapshot), `started_at`, and an empty `steps`.
2. **`propose-beliefs`**: load 17 entries, generate 182 candidate beliefs (writing `.forge/proposed-entries.json`), append the step record with `counts.entries` and `counts.proposed`, update `updated_at`.
3. **`accept-beliefs`**: apply gate to the 182 proposals; 0 pass; store remains at 123 beliefs; append the step with `counts.accepted` and `counts.total_beliefs`.
4. Compute `summary` from step counts, set `status: "completed"`, `completed_at`, final `updated_at`, and write the file.

On read, consumers typically do: read top-level `status`, then either use `summary` directly or locate steps by `name` to get step-specific `counts`.

## Invariants

- `status == "completed"` implies `completed_at` is present and all `steps[*].status == "completed"` (holds here).
- `updated_at >= started_at`; each step's `completed_at >= started_at`; step `started_at >= run started_at`.
- `steps` order encodes pipeline stage order: `propose-beliefs` precedes `accept-beliefs`.
- `summary.entries == propose.counts.entries`, `summary.proposed == propose.counts.proposed`, `summary.accepted == accept.counts.accepted`, `summary.total_beliefs == accept.counts.total_beliefs`.
- `accepted <= proposed`; here `0 <= 182`. Acceptance zero is not a failure.
- `total_beliefs` is a store snapshot from the accept stage, so it reflects post-accept state (123 before and after here).
- `counts` keys are step-specific — do not assume a fixed global schema.
- All timestamps are UTC ISO-8601 with offset `+00:00`.

## Error Handling

- This snapshot contains **no failure representation**, so the artifact itself is silent on how errors look. By convention, a failed run would set `status: "failed"` at the envelope and/or the offending step, and probably include error text in `detail` (or an extra field). Consumers should not rely on `detail` for machine parsing.
- **Partial-write risk:** because the file is overwritten in place, a crash mid-write could leave invalid JSON. This is mitigated only if the producer writes to a temp file and renames atomically — worth verifying in the writer (`report_gated.py` / `propose_update.py`).
- **Schema drift:** `counts` differs per step; strict deserializers that expect `entries`/`proposed` on every step will break. Consumers should select steps by `name`.
- **Timestamp ambiguity:** second-granularity timestamps collapse a sub-second run to identical values, so ordering must come from the array, not timestamp comparisons.
- **Zero-acceptance is a success case.** Any consumer that treats `accepted == 0` as failure would misread this file.
