# `.forge/report.json` — Pipeline Run Report

## Purpose

This is **not executable code** — it is a persisted, machine-readable **run report / audit artifact** for a pipeline named `diary-update`. It records the outcome of one pipeline execution: which steps ran, how long each took, how many items moved through each stage, and the final rollup totals.

Its responsibility is twofold:

1. **Observability** — give operators/consumers a single JSON document summarizing what the last diary-update run did (17 entries → 260 proposed beliefs → 0 accepted, fleet total 201).
2. **Input to gated reporting** — the `imported_by` list (`reasons/api.py`, `reasons_lib/report_belief.py`, `reasons_lib/report_gated.py`, and their tests) indicates these modules read this file at runtime to decide what to surface to users. "Imported by" here means the file path is *loaded/parsed* by those modules (a JSON file cannot be a Python import), so treat it as a data dependency, not a code dependency.

It is a **snapshot**, not an append-only log: there is one report file that is overwritten/updated per run (note the presence of `updated_at`, which could change during incremental progress, but in this instance equals everything else).

## Key Components (schema)

**Top-level fields**

| Field | Value | Contract |
|---|---|---|
| `pipeline` | `"diary-update"` | Stable identifier of the producer pipeline. |
| `started_at` | `2026-11-21T18:00:05+00:00` | ISO-8601 UTC start of the run. |
| `updated_at` | same | Last write timestamp; supports incremental rewriting. |
| `status` | `"completed"` | Terminal status enum (implicitly also `running`/`failed`, though not present here). |
| `steps` | array | Ordered list of step records. |
| `completed_at` | same | Set only on successful completion. |
| `summary` | object | Denormalized rollup of the step counts. |

**Step object schema** (each entry of `steps`)

- `name` — step identifier (`"propose-beliefs"`, `"accept-beliefs"`).
- `status` — `"completed"` here; same enum as parent.
- `started_at` / `completed_at` — ISO-8601 UTC timestamps.
- `detail` — human-readable string (`"proposed 260 from 17 entries"`, `"accepted 0 beliefs"`).
- `counts` — **free-form, step-specific** object (`{entries, proposed}` vs `{accepted, total_beliefs}`). This is the forward-extensibility hook: new steps add their own counters without changing the schema.
- `duration_seconds` — float; elapsed time for that step (0.01 each here).

**Concrete run content**

- Step 1 `propose-beliefs`: read **17 entries**, emitted **260 proposed** beliefs (written alongside to `.forge/proposed-entries.json`).
- Step 2 `accept-beliefs`: accepted **0** of the proposals; belief store remained at **201 total**.
- `summary`: `{entries: 17, proposed: 260, accepted: 0, total_beliefs: 201}` — a subset of all step counters, rolled up.

## Patterns

- **Audit/run-report artifact** — a serialized status document written at the end (and updated during) a pipeline, consumed by reporters.
- **Step-log pattern** — an ordered array of homogeneous step records with `status`/timing, rather than ad-hoc fields.
- **Denormalization for convenience** — `summary` duplicates data already present in `steps[].counts`. Consumers can read `summary` without iterating steps, at the cost of keeping two representations consistent.
- **Heterogeneous `counts` bag** — each step owns its own counter namespace; the parent schema doesn't constrain counter names.
- **UTC ISO-8601 everywhere** — all timestamps carry the explicit `+00:00` offset.
- **Single-file overwrite** — one `.forge/report.json` per repository, not a timestamped history (contrast with `costs/2026-11-19T180331-update.json`, which *is* timestamped).

## Dependencies

**Depends on:** nothing at the data level. It is pure JSON. Its producer is the diary-update pipeline (plausibly driven by `reasons/propose_update.py` / `reasons/cli.py`), and it is co-written with the companion artifact `.forge/proposed-entries.json`.

**Depended on by (consumers):**

- `reasons/api.py` — likely exposes run status via an API response.
- `reasons_lib/report_belief.py` — belief reporting that may include run provenance.
- `reasons_lib/report_gated.py` — gated surface that reads the run report to decide what may be shown.
- `tests/test_report_belief.py`, `tests/test_report_gated.py` — assert the reporters behave correctly against a report like this.

Because consumers are *readers of a file*, treat this schema as a **public contract**: changing keys or semantics breaks reporting and tests.

## Flow

1. **Producer starts** the `diary-update` pipeline → initializes the report: `pipeline`, `started_at`, `status` (presumably `"running"`), empty `steps`.
2. **`propose-beliefs` runs** — reads 17 diary entries, generates 260 candidate beliefs (persisted to `.forge/proposed-entries.json`), appends a step record with `counts: {entries: 17, proposed: 260}`.
3. **`accept-beliefs` runs** — evaluates the 260 proposals against the existing store, accepts 0, records `counts: {accepted: 0, total_beliefs: 201}`.
4. **Producer finalizes** — sets `status: "completed"`, fills `completed_at`/`updated_at`, and rolls step counters into `summary`.
5. **Consumers read** the file, parse it, branch on `status` and `summary` to render belief/gated reports or API responses.

Note the timing: all timestamps are identical (`18:00:05`) and each step is 0.01 s, i.e. a near-instant run. `duration_seconds` is per-step measured time and need not sum to wall-clock time.

## Invariants

A maintainer should assume the following are expected to hold (and would be worth adding schema validation for):

- `status` / step `status` are from a fixed enum; the terminal state `"completed"` implies `completed_at` is non-null.
- `started_at <= updated_at <= completed_at`. In this instance all are equal.
- `duration_seconds >= 0`.
- `steps` is **ordered** by execution: `propose-beliefs` precedes `accept-beliefs`.
- Step `name`s are unique within a run.
- `summary.entries == steps[propose].counts.entries` (17 ✔), `summary.proposed == steps[propose].counts.proposed` (260 ✔), `summary.accepted == steps[accept].counts.accepted` (0 ✔), `summary.total_beliefs == steps[accept].counts.total_beliefs` (201 ✔).
- `accepted <= proposed` (0 ≤ 260).
- Timestamps are UTC ISO-8601 with an explicit offset.
- `counts` is step-specific; **do not assume keys exist on all steps**.

⚠️ There is **no `schema_version` field**. For a persisted artifact with multiple consumers, this is a real maintenance risk — a future incompatible change cannot be detected by readers.

## Error Handling

There is no runtime error handling in a data file; the concerns are on the **consumer** side:

- Consumers must tolerate a **failed/partial run**: `status != "completed"`, missing `completed_at`, or a step whose `status` is not `"completed"`.
- JSON parse failures and missing keys (`summary`, `steps`, a step's `counts`) should be handled defensively — nothing in this document enforces their presence.
- This particular report represents a **fully successful** run (all statuses `"completed"`), so it exercises only the happy path; it provides no evidence of the failure-field naming (no `error`/`message` keys are demonstrated).
- The most operationally surprising signal here is `accepted: 0` out of `proposed: 260` — the pipeline succeeded but accepted nothing. Whoever consumes `report_gated.py` must treat "completed with zero accepted" as a legitimate, non-error state (likely the gating policy rejected all candidates).

## Beliefs

- `report-json-is-a-run-artifact` — `.forge/report.json` is a serialized `diary-update` pipeline run report consumed by reporting/API modules, not source code.
- `report-summary-mirrors-step-counts` — The `summary` object duplicates `steps[].counts` (17/260/0/201) and must stay consistent with the step records it rolls up.
- `report-status-completed-implies-completed-at` — The run and each step have `status: "completed"` and non-null `completed_at` timestamps.
- `report-steps-are-ordered` — `steps` is an execution-ordered array with `propose-beliefs` before `accept-beliefs`.
- `accept-beliefs-produces-zero-accepted` — The `accept-beliefs` step accepted 0 of 260 proposals, leaving `total_beliefs` at 201 while the run still reports `"completed"`.
- `report-json-has-no-schema-version` — The document carries no `schema_version` field, so consumers cannot detect incompatible schema changes.
