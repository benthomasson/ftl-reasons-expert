# File: .github/workflows/tests.yml

# `.github/workflows/tests.yml` — CI Test Pipeline

## 1. Purpose

This file is the **single CI entry point for the test suite**. It owns one responsibility: *every push to `main` and every pull request targeting `main` must install the project under four Python interpreters and run `pytest` against `tests/`.*

It is **not** a packaging/release workflow, not a lint/type-check workflow, and not a matrix for anything other than Python version. Notably, for a repo with `reasons/pg.py`, `reasons/pubsub.py`, `reasons/hf.py`, `reasons/network.py` and matching test files, this workflow **provisions no service containers and injects no secrets** — so it implicitly delegates "can't run here" decisions to the test suite itself (see §6).

## 2. Key Components

| Lines | Element | Contract |
|---|---|---|
| L1 | `name: Tests` | Display name in the Actions UI / required-status-check name. Renaming it breaks any branch-protection rule that pins `Tests / test (3.12)` etc. |
| L3–8 | `on: push/pull_request → branches: [main]` | Trigger filter. Only `main`; feature branches are covered only indirectly via `pull_request`. No `workflow_dispatch`, no `schedule`, no tag triggers. |
| L10–11 | `jobs.test` | One job, id `test`. The check name rendered in PRs is `test (3.10)` … `test (3.13)`. |
| L12 | `runs-on: ubuntu-latest` | GitHub-hosted runner; image rolls forward, so the Ubuntu version is a moving target across time. |
| L13–15 | `strategy.matrix.python-version: ["3.10","3.11","3.12","3.13"]` | Fan-out to 4 independent jobs. Because `fail-fast` is **not** set, it defaults to `true` (see §7). |
| L17 | `uses: actions/checkout@v4` | Default `fetch-depth: 1`, shallow clone, checked out at `$GITHUB_WORKSPACE` (repo root) — which becomes the cwd for all `run` steps. |
| L19–20 | `uses: astral-sh/setup-uv@v5` | Installs the `uv` binary and puts it on `PATH`. This action also auto-enables dependency caching when it finds a lockfile (see §6, note the lockfile caveat). |
| L22–23 | `run: uv python install ${{ matrix.python-version }}` | Downloads/manages the exact interpreter via uv's toolchain manager. There is **no** `actions/setup-python` step — Python comes exclusively from uv. |
| L25–26 | `run: uv run --extra test pytest tests/ -v` | The whole test contract in one line: resolve env → install project + `test` extra → exec pytest. |

### The one line that matters: `uv run --extra test pytest tests/ -v`

- `uv run` **creates/syncs `.venv`** in the workspace, installs the project from `pyproject.toml` in editable fashion (so `import reasons` / `import reasons_lib` resolve to the working tree, not to a wheel from PyPI), and *then* executes the command.
- `--extra test` pulls the optional dependency group named `test` (declared in `pyproject.toml`) into the environment. **pytest itself is never installed explicitly by this workflow** — it must be declared in that extra. If someone removes pytest from the `test` extra, this job fails at the `Run tests` step, not earlier.
- `pytest tests/ -v` — relative path, so it resolves against the repo root. `-v` is verbose; there is **no** `-x`, `--maxfail`, `--cov`, `-p no:cacheprovider`, `--junitxml`, `--durations`, or `-W error`. No report artifact is uploaded.

## 3. Patterns

- **Toolchain-as-action**: `astral-sh/setup-uv` + `uv python install` replaces the classic `setup-python` + `pip install` pair. Python versions are declared once (in the matrix) and consumed by uv, avoiding version drift between interpreter setup and package installation.
- **Declarative dependency groups over ad-hoc `pip install`**: the CI has zero knowledge of test dependencies; it only knows the *name* of the extra (`test`). This keeps the single source of truth in `pyproject.toml`.
- **Matrix fan-out with implicit fail-fast**: standard GH Actions idiom, but the default behavior (cancel siblings on first failure) is a deliberate-looking-but-likely-accidental choice — see §7.
- **Pinned-by-major-tag actions** (`@v4`, `@v5`): floating within a major version, so patch/minor updates arrive silently. Not SHA-pinned (no supply-chain hardening, no Dependabot/renovate lockstep).
- **Implicit cwd convention**: everything runs from the repository root, so any test relying on relative fixtures (e.g. `tests/…`, `.forge/report.json`) depends on this.

## 4. Dependencies

**Depends on (external):**
- `actions/checkout@v4`, `astral-sh/setup-uv@v5` — marketplace actions.
- The `uv` binary's toolchain download service (`uv python install`).
- `pyproject.toml` — specifically `[project.requires-python]` (must include 3.10–3.13) and the `test` extra / dependency-group containing `pytest`.
- The `tests/` directory and its `conftest.py` (fixtures, markers, skip logic).
- A lockfile *if* one exists at the repo root (`uv.lock`) — the file listing shows none, in which case `uv run` resolves fresh on every job.

**Depends on (internal):** the entire `reasons/` package (imported by the tests) and, transitively, whatever `reasons` imports at module load — which is why tests for `pg`, `pubsub`, `hf`, `network` must be import-safe without credentials.

**Imported by:** `tests/test_pg.py` (per the index). A YAML workflow cannot be Python-imported; the analyzer is most likely flagging a *string/path reference* — e.g. `test_pg.py` reads or asserts on `.github/workflows/tests.yml` (for instance to verify CI service configuration, or to derive a marker based on whether it's running in CI). Worth confirming before changing either file: a rename of this workflow would silently break that test's path lookup.

## 5. Flow

```
push to main ─┐
              ├─► create 4 matrix jobs (3.10, 3.11, 3.12, 3.13)
PR → main ────┘
                     │
        ┌────────────┴─────────────┐   (per job, sequential steps)
        │ 1. checkout@v4           │  shallow clone at $GITHUB_WORKSPACE
        │ 2. setup-uv@v5           │  uv on PATH (+ cache restore)
        │ 3. uv python install X   │  interpreter materialized
        │ 4. uv run --extra test   │  sync .venv (project + test extra),
        │    pytest tests/ -v      │  then exec pytest
        └──────────────────────────┘
                     │
        exit 0 → green check        exit ≠ 0 → red check (+ cancel siblings)
```

Data transformation is minimal: the only value flowing through the pipeline is `matrix.python-version` (a string from L15) interpolated into the step name (L22) and the install command (L23). Everything else is a side effect on the ephemeral runner.

## 6. Invariants

1. **Python support floor/ceiling = 3.10–3.13.** Any syntax newer than 3.10 (e.g. PEP 695 `type` statements, `match` is fine at 3.10) breaks the 3.10 job; any dependency that dropped 3.10 breaks it too. Conversely, `requires-python` in `pyproject.toml` must not exclude 3.13 or `uv run` will refuse the environment.
2. **pytest must be reachable via the `test` extra.** The workflow never installs it directly.
3. **Tests must be hermetic.** No `services:` block, no `env:` block, no secrets. Therefore anything in `tests/test_pg.py`, `test_pubsub.py`, `test_hf.py`, `test_network*.py`, `test_llm.py`, `test_mcp_server.py` etc. that needs Postgres, Pub/Sub, HF Hub, or an LLM endpoint **must self-skip** (via `pytest.skip`, `importorskip`, markers, or a `conftest.py` guard). If a skip guard is broken, CI goes red for reasons unrelated to the code under test.
4. **cwd = repo root, always.** Relative paths in tests and in `--extra test` resolution assume it.
5. **`tests/` must remain a directory of collectible tests**; the invocation hard-codes that path rather than relying on `testpaths` in config.
6. **All four interpreters must pass** for the `Tests` check to be green in aggregate (though see fail-fast below).
7. **No lockfile enforcement.** The command is not `uv run --frozen` / `--locked`, and the repo tree shows no `uv.lock`, so dependency resolution happens at run time → CI results are not bit-reproducible and can go red without any code change.

## 7. Error Handling

- **Fail-fast is on (implicitly).** `strategy` at L13 sets only `matrix`, so `fail-fast` defaults to `true`: the first matrix job to fail cancels the in-flight siblings. Practical consequence — a 3.10-only failure often surfaces as "3.11/3.12/3.13 cancelled", hiding whether the bug is version-specific. Adding `fail-fast: false` is the standard fix if you want full signal.
- **Step failure semantics:** a `run` step on Linux executes under `bash -e -o pipefail`, so a non-zero pytest exit fails the step, then the job. No `continue-on-error`, no retries, no `if: always()` cleanup/artifact steps — nothing is uploaded to diagnose failures beyond the raw `-v` log.
- **No timeouts.** No `timeout-minutes` at job or step level, so a hung test (network test without a skip guard, or an LLM call with no timeout) burns the default 360-minute job limit × 4 jobs.
- **No `permissions:` block** — the job inherits the repository's default `GITHUB_TOKEN` scope, which is more than the `contents: read` this workflow actually needs.
- **No `concurrency:` group** — successive pushes to the same PR stack duplicate 4-job runs instead of cancelling the superseded one (cost/noise issue, relevant given the repo tracks a `costs/` directory).
- **No `paths` filter** — doc-only or `.forge/`-only changes still spin the full 4× matrix.

## Topics to Explore

- [file] `pyproject.toml` — Confirm `requires-python` spans 3.10–3.13 and that the `test` extra (or dependency-group) actually declares `pytest`; also check whether `uv.lock` is meant to be committed.
- [file] `tests/conftest.py` — Where the skip guards for Postgres/network/LLM tests live; this is what makes a service-less CI runner viable.
- [file] `tests/test_pg.py` — Explains the "imported by" edge: how/why it references `.github/workflows/tests.yml`.
- [general] `ci-hardening` — Whether `fail-fast: false`, `concurrency`, `permissions: contents: read`, `--frozen`, and a `timeout-minutes` should be added.
- [general] `reasons-vs-reasons_lib` — Two near-identical module trees exist; determine which one the tests import and which one `pyproject.toml` packages, since `uv run` installs only the declared one.

## Beliefs

- `workflow-triggers-only-on-main` — The workflow runs on `push` and `pull_request` events filtered to the `main` branch, and has no `workflow_dispatch` or tag triggers.
- `test-matrix-has-four-python-versions` — The `test` job fans out over Python 3.10, 3.11, 3.12, and 3.13 on `ubuntu-latest`.
- `workflow-requires-test-extra-for-pytest` — pytest is installed solely through `uv run --extra test`, so removing pytest from the `test` extra in `pyproject.toml` breaks CI before any test executes.
- `workflow-provides-no-service-containers` — The job defines no `services:` or `env:` blocks, so tests requiring Postgres, Pub/Sub, HF, or network access must self-skip to keep CI green.
- `workflow-not-locked-to-resolved-dependencies` — The test command omits `--frozen`/`--locked`, so dependencies are re-resolved at run time rather than pinned by a committed lockfile.
- `matrix-fail-fast-defaults-to-enabled` — Since `fail-fast` is unspecified, the first failing Python version cancels the remaining matrix jobs.
